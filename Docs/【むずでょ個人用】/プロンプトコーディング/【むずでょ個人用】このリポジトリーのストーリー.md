# 【むずでょ個人用】このリポジトリーのストーリー

［きふわらべ］はコンピューター将棋の思考エンジン、コンピューター囲碁の思考エンジンの名前。  
きふわらべの開発者は、ペンネーム：むずでょ。ハンドル：Muzudho。
このリポジトリーの名前は KifuwarabeGo2026（きふわらべの碁２０２６）。  
もともと［きふわらべ］という名前で、  
2026年7月25、26日に開催された［２０２６年ＣＧＦオープン］というコンピューター囲碁大会に参加。  

その後、2026年8月に、囲碁だけでなく一般的な対戦ゲームにも対応することを目指して  
KifuwarabeGo の読み方を［きふわらべゲームオアシス］に変える案を Grok にもらう。  

## 対局ゲームについて思うこと

２０２６年現在、［チェッカー］、［オセロ］、［チェス］、［将棋］、［囲碁］、［連珠］などの対戦ゲームは、  
コンピューターを使った研究が進んでいる。  
例えば［オセロ］では６ｘ６の盤では引き分けというところまで解明されており、  
［将棋］では２７点法では先手勝率９割、２４点法では引き分けが多くなることが知られている。  
特に［将棋］では［定跡］が優秀で、定跡を持たないデスクトップＰＣに対して、定跡を使うノートＰＣがよく対抗できることが知られている。  
このように、  
ゲームの競技化や、ルールの公平性、レギュレーションの調整、勉強や研究が進むと、  
昔のチェスのチャンピオンである故・フィッシャーが言うような、  
［終盤のインスピレーションで勝敗が決まるエキサイティングなゲーム］というものが実現しにくくなっている。  
フィッシャーが考案した［チェス３６０］や［フィッシャー・クロックルール］は、  
だいたいそのような経緯から生まれている。  
将棋の故・米永邦雄永世棋聖はだいたい次のような説明を言っている。  
［自分のレベルに合った勉強をすること］  
連珠の第１回名人戦の２位の故・三森さんは、連珠について次のような説明をわたしにした。  
［プロに合わせてルールが変えられる。アマチュアが覚えるにはルールが難しくなった］  
また、ワールドトリガーという漫画のキャラクターの東春秋は次のようなことを言っている。  
［戦術で勝負するときは、敵の戦術レベルを計算に入れること］  
これらを踏まえ、わたしは、  
［プレイヤーのゲームに対する習熟度、ルールの公平性の調節、対戦相手の戦術レベル］  
この３つ全てが丁度良くないと、［辛すぎたり］［つまらなかったり］して、  
その原因を［ゲーム］に帰着させる誤りが起こっているのではないかと考えている。  
つまり、［永遠に面白いゲームのルールというものはない］と考えている。  
道路を色んな速度の車が走っている状態で、良い感じのドライビングができるのはその時々の状況だと思う。  
どちらかというと、  
［面白いゲームを作る］というよりは、［時々の面白い状況］を作り出したい。  
それは、  
［自分の望む設定、ゲームのルール、対戦相手の望む設定］という３大パラメーターで構成されると思う。  
その３大パラメーターを調整できるプラットフォーム構想に［ゲームオアシス］という名前を付けた。  
あとで説明する。  

## アプリケーションソフトについて思うこと

（１）時代１  

例えば、コンピューター将棋の場合は、［思考エンジン］だけがある頃は、  
人間が一手を入力し、［将棋エンジン］がそれに応える、という構造があった。  

例：1975年５月　早稲田大学の大学院生・瀧澤武信の将棋の思考エンジンと、推理作家・斎藤栄の対局

［将棋エンジン］の作成が流行りだすと、［将棋エンジン］同士の対局をしたくなる。  
人間側が［相手の将棋エンジン］の代打ちをすれば、［将棋エンジン］同士の仮想対局ができた。

## リポジトリーの構成について

最初は（コンピュータ囲碁ソフトだっただけに）［ＧＵＩ］と［思考エンジン］だけがあった。  
そのあと［ランチャー］を追加した。  

現在は、利用者との入出力を担当する［ＧＵＩ］と、処理や状態管理を担当する［エンジン］を分ける方針にしている。
また、利用場面を［ランチャー］、［ロビー（Lobby）］、［プレイルーム（Play Room）］の３段階に分け、
それぞれにＧＵＩとエンジンを置く。
さらに、人間の代わりに着手を選ぶ［プレイヤーエンジン］と、ゲーム運営を指示する［ゲームマスターエンジン］を設ける。

現在はまだ分割が終わっていないが、将来的には以下の８構成に分けることを目指す。

* （１）`ランチャーＧＵＩ` - いわゆる［ランチャー］。アプリケーションの導入、更新、起動を利用者が操作する画面。
* （２）`ランチャーエンジン` - インストール済みアプリケーションの管理や、導入、更新、起動の実処理を行うエンジン。
* （３）`ロビーＧＵＩ` - いわゆる［ロビー］。ゲーム選択や対局準備を利用者が操作する画面。
* （４）`ロビーエンジン` - いわゆる［コンシェルジュ］。参加者と各プログラムの接続を仲介し、ゲーム進行を統括するエンジン。
* （５）`プレイルームＧＵＩ` - いわゆる［プレイルーム］。対局、盤面編集、レビューなどを表示・操作する画面。
* （６）`プレイルームエンジン` - いわゆる［プレイスペース］。［囲碁］、［将棋］、［リバーシ］、［五目並べ］などのルールと、ゲームの現在の状態を管理するエンジン。
* （７）`プレイヤーエンジン` - 人間の代わりにゲーム上の行動を選ぶエンジン。
* （８）`ゲームマスターエンジン` - 人間のゲームマスターの代わりにゲーム運営を指示するエンジン。

その理由は、  
例えば［対局部分］だけを作りたい人は、［プレイルームＧＵＩ］または［プレイルームエンジン］に対象を絞って開発できるなど、  
分担ができる。  
［あなたは作りたいところだけ作る］が今考えたスローガン。  

## （１）［ランチャーＧＵＩ］（いわゆる［ランチャー］）の責務

* ユーザーがダブルクリックなどで直接起動する、システムの入口となる。
* 利用可能なアプリケーションと、そのインストール状況やバージョンを表示する。
* アプリケーションのインストール、バージョンアップ、起動を利用者が指示できるようにする。
* ランチャー自身の設定を表示・操作できるようにする。
* ユーザーから受け取った指示を［ランチャーエンジン］へ渡し、処理の進捗や結果を表示する。
* など。

## （２）［ランチャーエンジン］の責務

* 利用可能なアプリケーションと、インストール済みアプリケーションを管理する。
* 各アプリケーションのインストールとバージョンアップを実行する。
* ［ロビーＧＵＩ］など、入口となるアプリケーションを起動する。
* ランチャー自身の設定を保存し、必要に応じてランチャー自身をバージョンアップする。
* 通常はユーザーから直接起動されず、［ランチャーＧＵＩ］から利用される。
* など。

### ランチャーの起動とプログラム構成

ユーザーが直接ダブルクリックして実行するのは、原則として［ランチャーＧＵＩ］とする。
［ランチャーＧＵＩ］がユーザーの操作を受け取り、［ランチャーエンジン］へ処理を依頼する。

```text
ユーザー
  ↓ ダブルクリックして起動
ランチャーＧＵＩ
  ↓ 処理を依頼
ランチャーエンジン
  ↓
インストール／更新／アプリケーションの起動
```

プロジェクトを［ランチャーＧＵＩ］と［ランチャーエンジン］に分けることと、実行時のプロセスを分けることは別の問題である。
当面は、以下のように［ランチャーＧＵＩ］を実行ファイル、［ランチャーエンジン］を同じプロセス内から利用するライブラリーとする構成を基本とする。

```text
KifuwarabeGo2026.LauncherGui.exe
KifuwarabeGo2026.LauncherEngine.dll
```

将来、管理者権限を要する処理、バックグラウンド更新、障害からの復旧などのためにプロセスを分ける必要が生じた場合は、以下の構成も選択できる。

```text
KifuwarabeGo2026.LauncherGui.exe
  ↓ プロセス間通信
KifuwarabeGo2026.LauncherEngine.exe
```

いずれの構成でも、ユーザーから見た入口は［ランチャーＧＵＩ］とする。

### ゲームオアシス全体の段階的な通信方針

［ゲームオアシス］を構成するＧＵＩとエンジンは、将来、異なるプロセスや異なるプログラミング言語で実装できることを目指す。
ただし、最初からすべてをプロセス間通信にするのではなく、以下の段階を踏んで実装する。

#### 第１段階：同一プロセス内のインターフェース

ゲームオアシス全体について、最低限、この段階以上を目指す。

* ＧＵＩとエンジンの責務を分離する。
* 呼び出し側はエンジンの具象クラスへ直接依存せず、インターフェースを通して利用する。
* エンジンをライブラリーとして同じプロセス内から呼び出す。
* 通信方法に依存しない要求、応答、通知のデータ型を定める。

```text
ＧＵＩの実行ファイル
  ↓ 同一プロセス内のインターフェース呼び出し
エンジンのライブラリー
```

この段階ではプロセス間通信は発生しない。
インターフェースの実装を後から差し替えられるようにしておくことで、現在の実装を単純に保ちながら、第２段階へ移行できるようにする。

#### 第２段階：標準入出力と JSON によるプロセス間通信

別プロセス化の効果が大きい箇所や、異なるプログラミング言語による実装を接続したい箇所から、段階的に導入する。

```text
ＧＵＩまたは呼び出し側プロセス
  ↓ 子プロセスを起動
エンジンの実行ファイル

標準入力  → JSON の要求
標準出力  ← JSON の応答や通知
標準エラー出力 ← ログや診断情報
```

通信形式は、原則として１行に１個の JSON を記述する JSON Lines 形式とする。
標準出力にはプロトコル上のメッセージだけを書き出し、ログやデバッグ表示は標準エラー出力へ分離する。

要求と応答を対応付け、将来の拡張や互換性確認を行えるように、メッセージには識別番号、種類、プロトコルバージョンなどを含めることを検討する。

```json
{"version":1,"id":1,"type":"request","method":"checkForUpdates","params":{}}
{"version":1,"id":1,"type":"response","result":{"updatesAvailable":true}}
```

標準入出力と JSON を境界にすることで、呼び出し側とエンジン側を C#、Rust、その他の言語で個別に実装できるようにする。
第１段階で定めたインターフェースは維持し、その実装を［同一プロセス内のエンジンを呼ぶ実装］から［別プロセスへ JSON メッセージを送る実装］へ差し替えられる構成を目指す。

#### 第３段階：gRPC などによる通信

複数クライアント、双方向ストリーミング、厳密なスキーマからのコード生成などが必要になった場合は、gRPC やその他の通信方式を検討する。
これは現時点ですぐに実装する対象ではなく、第１段階と第２段階を運用した後の将来構想とする。

```text
第１段階：同一プロセス内のインターフェース
    ↓ 必要な箇所から移行
第２段階：標準入出力＋JSON
    ↓ 規模や要件が増えた場合に検討
第３段階：gRPC など
```

## （３）［ロビーＧＵＩ］（いわゆる［ロビー］）の責務

* 利用するゲームやアプリケーションを選択する画面を表示する。
* 対局者の名前を設定する画面を表示する。
* 思考エンジンの実行ファイルパスや、エンジンオプションを設定する画面を表示する。
* 盤サイズ、盤面の初期配置、持ち時間、ハンディキャップなど、ゲームの条件を設定する画面を表示する。
* ［プレイルームＧＵＩ］の開始を［ロビーエンジン］へ依頼する。
* など。

## （４）［ロビーエンジン］（いわゆる［コンシェルジュ］）の責務

* ［ロビーＧＵＩ］からゲームや対局条件の設定を受け取り、保持する。
* ［プレイルームＧＵＩ］、［プレイルームエンジン］、［プレイヤーエンジン］、［ゲームマスターエンジン］の接続を仲介する。
* ゲームの準備、開始、手番、時計、終了、記録などの進行を管理する。
* ゲームの開始に必要な各プログラムを起動し、終了時に後片付けする。
* など。

## （５）［プレイルームＧＵＩ］（いわゆる［プレイルーム］）の責務

* ［ロビーエンジン］から通知されたゲームの状態を、盤などで表示する。
* ［ロビーエンジン］から通知された結果を表示する。
* 人間による一手の入力を受け取り、［ロビーエンジン］へ渡す。
* 対局用、盤面編集用、レビュー用など、目的の異なるＧＵＩを用意できるようにする。
* 対局終了後はプレイルームを閉じ、ロビーへ戻れるようにする。
* など。

## （６）［プレイルームエンジン］（いわゆる［プレイスペース］）の責務

* ゲームルールと、現在のゲームの状態を保持する。
* プレイヤーの行動が合法か判定し、ゲームの状態へ適用する。
* 次の手番、終局、勝敗を判定し、結果を［ロビーエンジン］へ返す。
* など。

## （７）［プレイヤーエンジン］の責務

* ［ロビーエンジン］から与えられた局面に対して、人間の代わりに次の一手を選び、［ロビーエンジン］へ返す。

## （８）［ゲームマスターエンジン］の責務

* 人間のゲームマスターの代わりに、［ロビーエンジン］へ運営命令を出す。
* ゲームの開始、停止、再開、中止などを［ロビーエンジン］へ指示する。
* ハンディキャップや先後などの条件を決定する。
* 無勝負、失格、時間補正、打ち直しなどを裁定する。
* ルールだけでは判別できない例外状況を裁定する。

## 将来のプロジェクト名について

将来的には、プロジェクト名を以下の形式へ整理していく方針とする。

```text
KifuwarabeGo2026.{ProjectFamily}.{SubNamespace}
```

ここでいう［ProjectFamily］は、８つの役割、参照実装、ゲームの共有プログラムなど、プロジェクトの大きな分類を表す。
８つの役割と `.csproj` を必ず一対一にするという意味ではなく、１つの役割を複数のプロジェクトへ分割する場合も、同じ ProjectFamily の配下へまとめる。

### 製品本体

ランチャーとロビーについては、役割名を ProjectFamily として使用する。

```text
KifuwarabeGo2026.{RoleName}.{SubNamespace}
```

主な RoleName は以下の４つとする。

* `LauncherEngine`：ランチャーのエンジン。
* `LauncherGui`：ランチャーのＧＵＩ。
* `LobbyEngine`：ロビーのエンジン。いわゆる［コンシェルジュ］。
* `LobbyGui`：ロビーのＧＵＩ。いわゆる［ロビー］。

例えば、役割の内部をさらに分割するときは、以下のように命名する。

```text
KifuwarabeGo2026.LauncherEngine
KifuwarabeGo2026.LauncherEngine.Storage
KifuwarabeGo2026.LauncherGui
KifuwarabeGo2026.LauncherGui.Windows
KifuwarabeGo2026.LobbyEngine
KifuwarabeGo2026.LobbyEngine.Contracts
KifuwarabeGo2026.LobbyEngine.Storage
KifuwarabeGo2026.LobbyGui
KifuwarabeGo2026.LobbyGui.Windows
```

### 参照実装

ゲームマスターエンジン、プレイヤーエンジン、プレイルームＧＵＩ、プレイルームエンジンの参照実装は、以下の形式とする。

```text
KifuwarabeGo2026.Reference.{RoleName}.{ImplementationName}.{SubNamespace}
```

［ImplementationName］は、エンジンのハンドル名や、参照実装を識別する名前とする。

```text
KifuwarabeGo2026.Reference.GameMasterEngine.Standard
KifuwarabeGo2026.Reference.PlayerEngine.Kifuwarabe
KifuwarabeGo2026.Reference.PlayRoomGui.Standard
KifuwarabeGo2026.Reference.PlayRoomEngine.Standard
```

実装名や下位の名前空間を分ける必要がない段階では、末尾を省略してもよい。

```text
KifuwarabeGo2026.Reference.GameMasterEngine
KifuwarabeGo2026.Reference.PlayerEngine
KifuwarabeGo2026.Reference.PlayRoomGui
KifuwarabeGo2026.Reference.PlayRoomEngine
```

### ゲームの共有プログラム

特定のＧＵＩやエンジンだけに所属せず、複数の役割から利用するゲーム固有の型や処理は、以下の形式とする。

```text
KifuwarabeGo2026.Game.{GameName}.{SubNamespace}
```

例えば、囲碁やポン抜きの共有プログラムは以下のように命名する。

```text
KifuwarabeGo2026.Game.Go
KifuwarabeGo2026.Game.Go.Foundation
KifuwarabeGo2026.Game.Ponnuki
```

これにより、ゲーム固有の共有プログラムを［プレイルームＧＵＩ］、［プレイルームエンジン］、［プレイヤーエンジン］などのどれか１つへ無理に所属させずに済む。

### その他のプロジェクト

８つの役割へ直接当てはまらない細かなプロジェクトについても、用途を表す ProjectFamily の配下へ整理する。

```text
KifuwarabeGo2026.Protocol.{ProtocolName}
KifuwarabeGo2026.Shared.{LibraryName}
KifuwarabeGo2026.Tool.{ToolName}
KifuwarabeGo2026.Tests.{TestTarget}
```

プロジェクトを実際に改名または分割するときは、その時点の責務と依存関係を確認する。
現在のプロジェクト名を機械的に置き換えるのではなく、将来の構成へ段階的に近づけていく。
