# ゲーム構成要素と境界の用語整理

## 目的

`Provider Engine` という名称だけでは責務が伝わりにくいため、ゲームを構成するオブジェクトと、その境界に使う用語を整理します。

この文書では、ゲームルールを適用し、プレイヤーの行動によって状態を変化させるプログラムを「プレイスペースエンジン」と呼びます。

また、GUIからゲームの運営処理を切り離し、プレイヤー、ゲームマスター、GUI、プレイスペースエンジンを接続するコンピュータープログラムを「ゲームコンシェルジュ」と呼びます。

これは将来の設計に向けた用語案です。現行コードや既存プロトコルに残る `Provider` を、ただちに一括改名することを定めるものではありません。

## 表示名と内部名

利用者に見せる画面名には、施設のアナロジーを使った分かりやすい表示名を使用します。コード、プロトコル、アーキテクチャなどの技術的な文脈では、責務を表す内部名を使用します。

| 表示名 | 内部名 |
|---|---|
| Lobby | Concierge |
| Play Room | PlaySpace |

`Lobby` はゲームの受付、参加者やルールの選択、対局開始前の準備を行う画面を指します。`Play Room` は盤やゲーム状態を表示し、実際にプレイする画面を指します。画面上の表示名を変更しても、`Concierge` と `PlaySpace` の内部的な責務や、既存の型名、プロジェクト名、プロトコル名は変更しません。

## 全体像

```text
［プレイヤー］ ── P ──┐
［プレイヤー］ ── P ──┤
                          ├── ［ゲームコンシェルジュ］ ── G ── ［GUI］
［プレイヤー］ ── P ──┤                  │
                          │                  S
［ゲームマスター］─ M ──┘                  │
                              ［プレイスペースエンジン］
                                                   ├─ ゲームルール
                                                   ├─ ゲーム設定
                                                   └─ ゲーム状態
```

ゲームコンシェルジュはゲームの準備と進行を実行し、プレイヤー、ゲームマスター、GUI、プレイスペースエンジンを接続します。  
プレイスペースエンジンはルール、設定、現在状態を保持し、行動を適用した結果を返します。

ゲームコンシェルジュとプレイスペースエンジンはコンピュータープログラムです。プレイヤーとゲームマスターには、それぞれ人間またはコンピューターエンジンが参加できます。

## オブジェクト

### ゲームコンシェルジュ

ゲームコンシェルジュは、ゲームの準備、開始、手番、入力、判定依頼、例外対応、終了、記録を統括するコンピュータープログラムです。ホテルのコンシェルジュのように、参加者と各機能の間に立つ総合窓口に相当します。

GUIにこれらの処理を持たせると、表示とゲーム運営の責務が集中します。そのため、GUIから独立したプログラムとしてゲームコンシェルジュを設けます。

また、ゲームルールの適用と状態保持までゲームコンシェルジュに持たせると責務が大きくなるため、その処理はプレイスペースエンジンへ分離します。

主な責務は次のとおりです。

- プレイヤーの参加と手番の管理
- プレイヤーへ着手を要求し、応答を受け取る
- ゲームマスターから運営コマンドや裁定を受け取る
- ハンディキャップや初期局面など、ゲーム開始時の準備を実行する
- プレイスペースエンジンへ行動の適用を依頼する
- プレイスペースエンジンから得た結果をGUIとプレイヤーへ通知する
- 現在の状態と権限を検証して、運営コマンドを実行する
- ルールだけでは決められない例外状況の裁定をゲームマスターへ問い合わせる
- 時計を進行させる
- ゲームの開始と終了を管理する
- 棋譜を作成する

ゲームコンシェルジュは総合窓口ですが、すべてを一つの巨大なクラスへ実装することを意味しません。初期局面生成、時計、記録、権限確認などを内部の専門オブジェクトへ委譲できます。

### ゲームマスター

ゲームマスターは、ゲームの運営方針を決め、ゲームコンシェルジュへコマンドを送る参加者です。人間またはコンピューターエンジンが担当できます。

主な責務は次のとおりです。

- ハンディキャップ、先後、初期局面などの条件を決める
- ゲームの開始、一時停止、再開、中止を指示する
- ルールだけでは判別できない状況を裁定する
- 無勝負、失格、時間補正、打ち直しなどを指示する
- 配信、大会、視聴者参加企画などの運営方針を反映する

ゲームマスターは必須とは限りません。人間の裁定を必要としないゲームでは、自動ゲームマスターを接続するか、既定の運営方針をゲームコンシェルジュが使用します。

### プレイヤー

プレイヤーはゲームコンシェルジュへ接続し、対局者としてゲームへ参加する人間またはコンピューターエンジンです。

基本的な責務は、ゲームコンシェルジュから局面と手番を与えられ、その局面で選んだ一手を応答することです。

### GUI

GUIは、設定の編集、ゲームへの入力、観戦、研究、および各画面へのナビゲーションを提供します。  
「きふわらべの碁2026」はGUIを含みます。

GUIはルール、進行、裁定を独自に確定せず、利用者の操作をゲームコンシェルジュへ渡し、ゲームコンシェルジュから通知された状態と判定結果を表示します。

### プレイスペースエンジン

プレイスペースエンジンとは、ゲームルールを適用し、プレイヤーの行動によってゲーム状態を変化させるプログラムです。

ここでいう「スペース」は、囲碁盤のような物理的な場所だけを指しません。  
囲碁の四択クイズなら、問題、選択肢、回答状況、得点などが存在して変化する論理的な場所も管理対象です。

プレイスペースエンジンは次のものを含みます。

- ゲームルール
- ゲーム設定
- 現在のゲーム状態

プレイスペースエンジンは次のものを含みません。

- プレイヤー
- GUI
- ゲームマスター
- 棋譜など、ゲームの外部へ保存する記録

プレイスペースエンジンは行動を受け取り、少なくとも次の結果を返します。

- 行動を受理できるか
- 行動適用後の状態
- 盤上から取り除かれた石や駒
- 次の手番
- ゲームが終了したか
- 勝者と終了理由

### ゲームルール

ゲームルールは、プレイスペースエンジンが状態を変化させるときに従う規則です。  
ゲームルール自体は、ゲームを動かす主体ではないため「エンジン」とは呼びません。

ゲームルールは、次の判断方法を定めます。

- 着手や回答などの行動が合法か判定する
- 行動適用後の状態を計算する
- 盤上から取り除かれる石や駒を計算する
- 終了条件と勝敗を判定する

囲碁、五目並べ、リバーシ、チェスなどは「ゲーム種別」です。日本ルールや中国ルールなど、同じゲーム種別の中で異なる規則は「ルールセット」と呼びます。

### ゲーム設定

ゲーム設定は、プレイスペースエンジンの動作を決める静的なデータです。独立したプレイ対象や、ゲームコンシェルジュと接続する能動的なオブジェクトではありません。

```text
ゲーム設定
├─ ルール設定
│  ├─ ルールセット
│  ├─ 盤サイズ
│  ├─ コミ
│  └─ 禁止手など
├─ 進行設定
│  ├─ ゲーム形式
│  ├─ 初期局面
│  └─ 終了条件
└─ 時計設定
   ├─ 基本時間
   └─ 秒読み
```

持ち時間の設定値はゲーム設定に含めますが、時計の進行は原則としてゲームコンシェルジュが担当します。  
時間切れを勝敗へ反映する必要がある場合は、その事象をプレイスペースエンジンへ渡します。

### ゲーム状態

ゲーム状態は、ゲーム開始後に変化するデータです。

- 現在の局面
- 現在の手番
- アゲハマや得点
- キャスリング権など、以後の合法手へ影響する状態
- 終了状態と勝敗

ゲーム設定とゲーム状態を分けることで、「開始時に決める値」と「プレイ中に変化する値」を区別します。

## 境界

| 記号 | 推奨名称 | 接続対象 | 主な内容 |
|---|---|---|---|
| P | プレイヤープロトコル | ゲームコンシェルジュとプレイヤー | 着手要求、着手応答、着手通知、投了 |
| M | ゲームマスタープロトコル／ゲーム運営プロトコル | ゲームコンシェルジュとゲームマスター | 運営設定、開始、停止、再開、裁定、運営命令 |
| G | GUIプロトコル | ゲームコンシェルジュとGUI | 操作入力、状態通知、表示更新、画面遷移 |
| S | プレイスペースプロトコル／プレイスペースAPI | ゲームコンシェルジュとプレイスペースエンジン | 初期化、行動適用、状態取得、終局結果 |
| C | 設定スキーマ／設定API | プレイスペースエンジンとゲーム設定 | 設定の記述、読み込み、検証、適用 |

P、M、G、S、Cは、特定のデータ形式ではなく「どの役割同士を接続する境界か」を示す記号です。実装時には、それぞれの境界に適した通信方式やAPIを選びます。

### プロトコルP

プレイヤーとの境界です。GTPは代表的な実装候補です。

ゲームコンシェルジュはプレイヤーへ「この局面で一手を選ぶ」よう要求し、プレイヤーは選んだ着手を応答します。また、他プレイヤーの着手やゲーム終了など、進行に必要な情報をゲームコンシェルジュから通知します。

### プロトコルM

ゲームマスターとの境界です。人間のゲームマスターは運営用GUIなどを通じて接続でき、コンピューターエンジンのゲームマスターはAPIまたは通信プロトコルを通じて接続できます。

ゲームマスターはハンディキャップ、初期局面、開始、停止、再開、時間補正、無勝負、失格などの運営コマンドを送ります。ゲームコンシェルジュは権限と現在状態を検証してコマンドを実行し、その結果と操作履歴を通知します。

### プロトコルG

GUIとの境界です。JSONなどの構造化データを利用できます。

GUIからは利用者の操作を入力し、ゲームコンシェルジュからは局面、消えた石、手番、棋譜、結果などを通知します。GUIは通知を受けて画面表示を更新します。

### プレイスペースプロトコル／プレイスペースAPI S

ゲームコンシェルジュとプレイスペースエンジンの境界です。  
ゲームコンシェルジュが初期設定やプレイヤーの行動を渡し、プレイスペースエンジンが受理の可否、適用後の状態、次の手番、終局状態などを応答します。

ゲームコンシェルジュは、プレイスペースエンジン内部のルール計算方法や状態保持方法を知る必要がありません。

GTPまたは独自プロトコルを通信手段として利用することは可能ですが、GTPの一般的な主用途はプレイヤーエンジンの操作です。そのため、境界Sの役割はGTPそのものとは分けて定義します。

SGFは主に棋譜やゲーム木を保存・交換するデータ形式です。  
境界Sで局面や着手列を受け渡す形式として利用することはできますが、プレイスペースプロトコル自体とは区別します。

### 設定スキーマ／設定API C

プレイスペースエンジンがゲーム設定を解釈する境界です。  
内部実装だけで完結する場合は、独立した通信プロトコルを設ける必要はありません。

設定項目の型、既定値、許容範囲、相互制約を表す場合は「設定スキーマ」、設定の取得、検証、適用を操作として提供する場合は「設定API」と呼び分けます。

## ゲームの分類

| 用語 | 意味 | 例 |
|---|---|---|
| ゲーム種別 | 基本となるゲームのカテゴリー | 囲碁、連珠、リバーシ、チェス |
| ゲーム形式 | ゲームの遊び方や進行形式 | 通常対局、指定局面戦、ポン抜き、四択クイズ |
| ルールセット | 同じゲーム種別における規則の違い | 日本ルール、中国ルール、純碁 |
| ゲーム設定 | プレイスペースエンジンを初期化する値 | 9路、コミ6目半、初期局面 |
| ゲームセッション／対局 | 実際に開始された一回のゲーム | 2026年8月22日に開始した黒対白の対局 |

「囲碁対局」「指定局面戦」「ポン抜き」などを独立したプログラムという意味で「ゲームアプリ」とは呼びません。  
ここではプログラムの配布単位ではなく、プレイスペースエンジン上で提供される遊び方として「ゲーム形式」に分類します。

## `Provider Engine` の扱い

`Provider Engine` は、初期局面の生成、着手監視、ルール判定、終局判定、状態保持など複数の責務を含み得るため、名称だけでは役割を特定しにくい用語です。

新しい設計では、実際の責務に応じて次の語へ分解します。

- プレイヤーの行動へルールを適用し、状態を変化させるもの: プレイスペースエンジン
- ゲームの準備、進行、仲介、例外対応を実行するもの: ゲームコンシェルジュ
- ゲームの運営方針と裁定を決める参加者: ゲームマスター
- プレイスペースエンジンが従う規則: ゲームルール
- ゲームコンシェルジュとプレイスペースエンジンの境界: プレイスペースプロトコル／プレイスペースAPI
- ゲーム開始時の条件を表すもの: ゲーム設定
- ゲーム中に変化するもの: ゲーム状態

既存の `Provider` コマンドや文書は互換性のために旧称として残し、変更するときはプロトコル互換性と移行手順を別途定めます。

## 将来の拡張

この分離により、GUIへゲーム運営やルール処理を集中させず、ゲームコンシェルジュとプレイスペースエンジンを独立して差し替えられます。  
また、人間またはコンピューターエンジンのプレイヤーとゲームマスターを、それぞれ独立した参加者として接続できます。  
さらに、プレイスペースエンジン内部のゲームルール、ルールセット、ゲーム形式を組み替えられます。

通常の囲碁だけでなく、変則囲碁、囲碁の四択クイズ、連珠、リバーシ、チェスなどへの拡張を想定できます。

## Kifuwarabe Game Oasis構想

### 製品名の二つの意味

`Kifuwarabe Go` は、次の二つの側面を持つ製品名とします。

- 囲碁（Go）を遊ぶための囲碁プログラム
- 複数のゲーム、参加者、エンジンが集まるゲームプラットフォーム `Kifuwarabe Game Oasis`

`Go` は囲碁を表すと同時に、`Game Oasis` を縮めた愛称でもあります。

ゲームプラットフォームとしての説明には「ゲームオアシス」または `Kifuwarabe Game Oasis` を使用します。

### 代表的なプレイスペース

最初の代表的なプレイスペースとして、次の二つを用意する構想です。

| プレイスペース | 目的 | 主な相違点 |
|---|---|---|
| 通常囲碁 | 通常の囲碁対局、研究、観戦 | 囲碁の合法手、コウ、パス、終局、勝敗判定 |
| ポン抜き | 入門、配信企画、実験的なゲーム | 初期配置、ハンディキャップ、石を取ることによる終了判定 |

通常囲碁とポン抜きを同じ境界Sへ接続することで、囲碁固有の処理がGUIやゲームコンシェルジュへ混入していないかを検証できます。

```text
［Kifuwarabe Game Oasis］
├─ GUI
├─ ゲームコンシェルジュ
├─ プレイヤー接続
├─ ゲームマスター接続
└─ プレイスペース
   ├─ 通常囲碁
   └─ ポン抜き
```

## 将来のC#プロジェクト構成案

この節は将来の大規模な仕様変更に向けた構想です。現時点ではプロジェクトの作成、改名、移動、参照変更を実施しません。

この再構成はv4.0.0の破壊的変更として扱います。現行プロジェクトからの詳細な分割・統合・移行方針は、[`v4.0.0プロジェクト再構成計画.md`](../開発/ゲームオアシス構想/v4.0.0プロジェクト再構成計画.md)を参照してください。

### Game Oasis本体に属するプロジェクト

`KifuwarabeGo2026.GameOasis.*` の下には、ゲームオアシスの境界契約と公式コンシェルジュを置きます。プレイヤー、ゲームマスター、GUI、プレイスペースの各実装は、境界の外側から接続されるため、この名前空間の下には置きません。

境界契約を所有するプロジェクト名には、`KifuwarabeGo2026.GameOasis.Contracts` を採用します。`KifuwarabeGo2026.Contracts` という製品全体を対象に見える名称は使用せず、契約の所有者がGame Oasisであることを名前で明示します。

```text
KifuwarabeGo2026.GameOasis.Contracts
KifuwarabeGo2026.GameOasis.Concierge
```

| プロジェクト | 所有するもの |
|---|---|
| `KifuwarabeGo2026.GameOasis.Contracts` | プロトコルP、M、G、Sの契約、コマンド、応答、通知、共通識別子、エラー、能力情報 |
| `KifuwarabeGo2026.GameOasis.Concierge` | セッション、参加者、進行、時計、記録、権限確認、運営コマンド、プレイスペースの呼び出し |

Contractsは最初は一つのC#プロジェクトとし、境界ごとに名前空間を分けます。

```text
KifuwarabeGo2026.GameOasis.Contracts.Common
KifuwarabeGo2026.GameOasis.Contracts.ProtocolP
KifuwarabeGo2026.GameOasis.Contracts.ProtocolM
KifuwarabeGo2026.GameOasis.Contracts.ProtocolG
KifuwarabeGo2026.GameOasis.Contracts.ProtocolS
```

必要性が明らかになった場合は、将来それぞれを別アセンブリまたは別パッケージへ分割できます。

### 公式の参照実装

Kifuwarabe Goリポジトリーで用意するプレイヤー、ゲームマスター、GUI、プレイスペースは、Game Oasisへ外側から接続する公式の参照実装と位置づけます。名前には学習用・非本番用という印象が強い `Examples` を使用せず、契約の模範となる実装を示す `KifuwarabeGo2026.Reference.*` を採用します。

```text
KifuwarabeGo2026.Reference.PlayerEngine
KifuwarabeGo2026.Reference.GameMasterEngine
KifuwarabeGo2026.Reference.Gui
KifuwarabeGo2026.Reference.PlaySpace.Go.Foundation
KifuwarabeGo2026.Reference.PlaySpace.Go
KifuwarabeGo2026.Reference.PlaySpace.Ponnuki
```

| 参照実装 | 使用する主な契約 | 所有するもの |
|---|---|---|
| `KifuwarabeGo2026.Reference.PlayerEngine` | プロトコルP | 公式のコンピュータープレイヤー実装 |
| `KifuwarabeGo2026.Reference.GameMasterEngine` | プロトコルM | 公式の自動ゲームマスター実装 |
| `KifuwarabeGo2026.Reference.Gui` | プロトコルG | 公式GUIと人間参加者向けの操作アダプター |
| `KifuwarabeGo2026.Reference.PlaySpace.Go.Foundation` | 参照実装内部 | 囲碁座標、石、盤、連、呼吸点など、通常囲碁とポン抜きで共有する囲碁基盤 |
| `KifuwarabeGo2026.Reference.PlaySpace.Go` | プロトコルS | 通常囲碁の設定、状態、合法手、行動適用、終局、勝敗判定 |
| `KifuwarabeGo2026.Reference.PlaySpace.Ponnuki` | プロトコルS | ポン抜きの設定、初期局面、ハンディキャップ、行動適用、終了、勝敗判定 |

`Go.Foundation` は候補名です。実装開始時に `Go.Domain` などと比較して最終決定します。

参照実装はGame Oasis本体の内部実装ではありません。別リポジトリーの開発者も、自分の組織または製品の名前空間を使用して独立した実装を作成できます。

Game Oasisの公開識別子について、きふわらべ公式実装は`io.github.muzudho.kifuwarabego2026`を所有ルートとします。識別子比較は大文字と小文字を区別しますが、公式発行値はASCII小文字、数字、ピリオド、ハイフンだけで構成します。外部実装は自分が所有・管理できる名前空間を使用します。詳細と移行判断は`開発/ゲームオアシス構想/v4.0.0プロジェクト再構成計画.md`の「公開識別子の命名規約」を参照します。

現在はC#版Contractsと参照実装を先に完成させます。将来はプレイヤーエンジン、ゲームマスターエンジン、GUIエンジン、プレイスペースエンジンのすべてを、コンピューター言語を問わず接続できるテキストベース仕様へ展開します。テキスト形式と配送方式はC#版で意味契約を検証した後に決定し、現段階では固定しません。

```text
AliceGames.PonnukiPlaySpace       → ProtocolS
BobEngines.StreamingGameMaster   → ProtocolM
ExampleCompany.GoPlayer          → ProtocolP
```

### Game Oasisの外側に置くプロジェクト

製品の起動基盤と汎用UIライブラリーは、Game Oasisを利用または起動する外側の部品であり、ゲームオアシスの実行モデルには含めません。

```text
KifuwarabeGo2026.Launcher
KifuwarabeGo2026.Launcher.Core
KifuwarabeGo2026.Launcher.Platform
KifuwarabeGo2026.Launcher.Presentation
KifuwarabeGo2026.StationeryUI
```

- `Launcher.*` はインストール、更新、バージョン管理、実行ファイルの起動、プラットフォーム固有処理を所有します。
- `StationeryUI` はボタン、付箋、入力部品、Canvasなどの汎用的なMonoGame UI部品を所有します。
- これらはGame Oasisから利用されても、Game Oasis固有のゲーム運営やルールを所有しません。

### 現行プロジェクトの扱い

#### `KifuwarabeGo2026.Match`

現行の `MatchSession` は囲碁盤、合法手、石の取得、コウ、パス、投了、局面、終局状態などを所有しています。そのため、名称は `Match` ですが、将来構成では主として通常囲碁のプレイスペースに相当します。

将来は内容を確認しながら、主に次の移行先へ分解します。

```text
KifuwarabeGo2026.Match
    ├─ 囲碁ルールと状態 → KifuwarabeGo2026.Reference.PlaySpace.Go
    └─ 時計や運営処理   → KifuwarabeGo2026.GameOasis.Concierge
```

特に時計はゲーム設定として時間値を受け取りますが、時計を実際に進行させる責務はゲームコンシェルジュ側に置きます。

#### `KifuwarabeGo2026.Shared`

`Shared` は長期的な所有者名として使用せず、内容を実際の所有者へ戻します。

```text
GoBoard、GoPoint、GoStone、盤面解析
    → KifuwarabeGo2026.Reference.PlaySpace.Go.Foundation

ApplicationFamilySettingsなどの製品共通設定
    → Launcherまたは将来の製品設定用プロジェクト
```

`Shared` をそのまま `GameOasis.Shared` へ改名すると、異なる責務を再び一つの箱へ集めることになるため行いません。

### 目標とする参照方向

ContractsはGame Oasisの内側と外側を接続する契約です。各実装は自分に必要な契約を参照し、Contractsは各実装を参照しません。GUIは具体的な通常囲碁やポン抜きの実装を直接参照せず、ゲームコンシェルジュを通じて利用します。

```text
［Reference.PlayerEngine］ ── P ──┐
［Reference.GameMasterEngine］─ M ─┤
［Reference.GUI］────────── G ──────┼── ［GameOasis.Concierge］
                                   │
［Reference.PlaySpace.Go］──── S ───┤
［Reference.PlaySpace.Ponnuki］─ S ─┘

すべての実装 ──参照──→ ［GameOasis.Contracts］
［GameOasis.Contracts］ ──×──→ 各実装
```

`Contracts` は境界を越える契約だけを所有し、GUI、MonoGame、コンシェルジュの具象実装、特定のプレイヤー、ゲームマスター、プレイスペース実装へ依存しません。通信が双方向でも、C#プロジェクトの参照は各実装からContractsへの一方向です。

### プロトコルの実装方針

プロトコルGとSの「プロトコル」は、最初から別プロセス通信を必須とするものではありません。まず同一プロセス内のC#インターフェースとデータ契約として実装し、必要になったときにJSON、標準入出力、ソケットなどの通信アダプターを追加します。

プロトコルGでは画面座標、ボタン、ダイアログなどの描画詳細を渡さず、「ポン抜きを選択した」「ゲームを開始する」などの意味を持つ操作と、表示に必要な状態を渡します。

プロトコルSの最小候補は次のとおりです。

- プレイスペースの種類と能力を取得する
- 設定スキーマを取得する
- ゲーム設定を検証する
- プレイスペースを初期化する
- 現在状態を取得する
- 行動を適用する
- 適用結果とゲームイベントを取得する
- 終了状態と勝敗を取得する
- セッションを破棄する

### 想定する移行順序

大きな一括改名や一括移動は行わず、動作する縦方向の経路を一本ずつ作ります。

1. 通常囲碁とポン抜きの代表的な操作シナリオを記述する。
2. `GameOasis.Contracts` に最小のプロトコルSを定義する。
3. `GameOasis.Concierge` を作り、GUIにある運営処理を段階的に移す。
4. GUIの必要に合わせてプロトコルGを定義する。
5. 比較的小さなポン抜きを最初の `Reference.PlaySpace` として切り出す。
6. GUI、ゲームコンシェルジュ、ポン抜きが接続された一本の経路を検証する。
7. 同じ契約を使って通常囲碁を切り出す。
8. `Match` と `Shared` の残った責務を所有者別に移す。
9. 必要になった場合だけ別プロセス通信を追加する。

### この構想で現時点では行わないこと

- C#プロジェクトの作成、改名、削除、移動
- 名前空間とアセンブリ名の一括変更
- プロジェクト参照の変更
- 現行 `Provider` プロトコルの削除
- GUIから既存処理を移動する実装作業
- プロトコルG、M、Sのデータ形式の確定

実装を開始する前に、境界契約、移行単位、互換性、テスト方法を改めて確認します。
