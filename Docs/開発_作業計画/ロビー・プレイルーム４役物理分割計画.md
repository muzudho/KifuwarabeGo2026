# ロビー・プレイルーム4役物理分割計画

状態：計画作成（2026年8月29日）

## 目的

現在の`KifuwarabeGo2026.GameOasis.*`に残る役割固有コードを、次の4つのProjectFamilyへ段階的に物理分割します。

1. `KifuwarabeGo2026.LobbyGui`：ゲーム開始前の選択、設定、登録、起動操作。
2. `KifuwarabeGo2026.LobbyEngine`：カタログ、永続化、構成、セッション準備。
3. `KifuwarabeGo2026.Reference.PlayRoomGui.*`：ゲーム中、盤面編集、レビュー、観戦の表示と入力。
4. `KifuwarabeGo2026.Reference.PlayRoomEngine.*`：局面、合法手、状態遷移、終局、結果。

`KifuwarabeGo2026.GameOasis`は廃止しません。複数の役割が共有する契約、Conciergeによる調停、構成点、互換実行ホストだけを所有する横断ProjectFamilyとして残します。

## 先行計画との関係

先行する[`ロビーのＧＵＩとエンジン分割計画.md`](./ロビーのＧＵＩとエンジン分割計画.md)では、同一プロセス境界、`ILobbyEngine`、`LobbyGuiController`、Play Room起動契約、JSON Lines Host、Protocol S SDKまでを整備しました。

本計画はその後続です。論理境界を作り直すのではなく、安定した境界に沿ってソース、プロジェクト参照、実行ホスト、発行物を物理的に分けます。

将来構想の[`Lobby・PlayRoom実行ファイル分離移行計画.md`](../開発/ゲームオアシス構想/Lobby・PlayRoom実行ファイル分離移行計画.md)は参考にしますが、既存の保存形式、公開実行ファイル名、ランチャー起動経路を一括変更しません。

## 完了像

```text
LauncherEngine
  └─起動─> LobbyGui.Windows
               │
               ├─> LobbyEngine
               │     ├─ Application
               │     ├─ Storage
               │     └─ JSON Lines Host
               │
               └─起動要求─> PlayRoomGui.<Implementation>
                                  │
                                  ├─ Protocol G ─> GameOasis.Concierge
                                  └─ Protocol S ─> PlayRoomEngine.<Implementation>

GameOasis.Contracts   （4役が共有する言語・通信非依存契約）
GameOasis.Concierge   （Protocol G/P/S/Mの横断調停）
GameOasis.Gui.Windows （移行中の互換ホスト。最終的な要否を再評価）
```

物理分割後も、同一プロセス実装とJSON Lines実装を同じ契約の差し替えとして維持します。

## 現状

### 既に分離済みの境界

* `KifuwarabeGo2026.LobbyEngine`、`LobbyEngine.JsonLines`、`LobbyEngine.JsonLinesHost`。
* `ILobbyEngine`、`LobbyGuiController`、`ILobbyGuiCommands`。
* `PlayRoomLaunchRequest`、`PlayRoomLaunchResult`、`IPlayRoomLauncher`。
* Board Editor、Review、Matchの`PlayRoom.*.JsonLinesHost`。
* `IPlaySpaceProtocol`と`PlaySpace.JsonLines`のクライアント／サーバーSDK。
* Protocol G、P、S、MとConciergeの調停境界。
* PlaySpace適合性ランナーとJSON Schema／テストベクトル。

### 主な混在

* `GameOasis.Gui/Game1.cs`がロビー画面、プレイルーム画面、画面遷移、構成を所有する。
* `GoAppSession`が開始前の選択状態と開始後の局面・棋譜・対局状態を所有する。
* `GameOasis.Gui`にLobby、Local Match、CGOS、Board Editor、Review、囲碁・ポン抜き表示が同居する。
* `GameOasis.Application`と`GameOasis.Storage`にロビー固有のカタログ責務が残る。
* 現在のPlay Room独立Hostは主にエンジン側であり、独立したPlay Room GUI ProjectFamilyは未作成である。

## 所有ルール

### `LobbyGui`

* ゲーム、プレイスペース、参加者、ゲームマスター、対局条件の選択と編集。
* 設定画面、エンジン管理、CGOS接続先管理。
* `PlayRoomLaunchRequest`の作成と開始結果の表示。
* 局面の合法性、手番、勝敗を所有しない。

### `LobbyEngine`

* カタログの正本、正規化、保存ユースケース。
* 利用可能な実装の探索とセッション準備。
* GUI型、MonoGame型、ゲーム局面型を所有しない。

### `Reference.PlayRoomGui.<Implementation>`

* ゲーム中、観戦、編集、レビューの表示と入力。
* Protocol GまたはPlay Room公開契約だけで外側と接続する。
* 永続カタログ、外部実装のインストール、ゲームルールの正本を所有しない。

### `Reference.PlayRoomEngine.<Implementation>`

* ゲーム設定の検査、セッション、状態、行動、リビジョン、終局、結果。
* Protocol Sを公開し、GUI、MonoGame、ロビーの保存型を参照しない。

### `GameOasis`

* 4役が共有する公開契約と識別子。
* Protocol G/P/S/M間の調停。
* 移行中または製品全体の構成点。
* 役割固有の画面、保存処理、ゲームルールを恒久的に集積しない。

## 依存方向

```text
LobbyGui ---------------------> LobbyEngine contracts
LobbyGui ---------------------> GameOasis.Contracts
PlayRoomGui.<Game> -----------> GameOasis.Contracts
PlayRoomEngine.<Game> --------> GameOasis.Contracts
GameOasis.Concierge ----------> GameOasis.Contracts

LobbyEngine.Application -----> GameOasis.Contracts（必要な共通型だけ）
LobbyEngine.Storage ---------> LobbyEngine.Application

禁止：LobbyEngine -----------> MonoGame / PlayRoomGui
禁止：PlayRoomEngine --------> LobbyGui / LobbyEngine.Storage / MonoGame
禁止：GameOasis.Contracts ---> 具象実装
禁止：ゲーム固有実装間の相互参照
```

## 互換性方針

* 現行`KifuwarabeGo2026.GameOasis.Gui.Windows.exe`と旧別名を、移行完了までは維持する。
* ランチャーの登録情報と更新経路を先に壊さない。
* GTPエンジン、参加者、CGOS、アプリケーション設定、SGFの保存形式を維持する。
* 同一プロセス版を安全な復旧経路として残してから、別プロセス版を既定にする。
* `GameOasis.Contracts`のProtocol版を破壊的に変更しない。必要なら新しい版を追加する。

## 作業段階0：基準と所有一覧を固定する

目的：物理移動による欠落を検出できる基準を作ります。

作業：

* `Game1`、`GoAppSession`、Application、Storage、Conciergeの型を5分類する。
  * Lobby GUI
  * Lobby Engine
  * Play Room GUI
  * Play Room Engine
  * Game Oasis横断
* ロビー、Board Editor、Review、Match、CGOS、ポン抜きの画面遷移と状態所有を記録する。
* 現在のプロジェクト参照グラフと発行物を固定する。
* Smart App ControlによるOS拒否をコード試験失敗と分けて記録する。

完了条件：全対象型に移行先または残置理由があり、既存テストと手動確認項目が一覧化されている。

## 作業段階1：Lobby Engineの物理所有を完成する

目的：ロビーの正本と保存を`LobbyEngine` ProjectFamilyへ集めます。

作業：

* `GameOasis.Application`のロビー固有プロフィール、カタログ、ユースケースを`LobbyEngine.Application`へ移す。
* `GameOasis.Storage`のロビー固有実装を`LobbyEngine.Storage`へ移す。
* 囲碁固有のGTPプロフィールを汎用ロビー契約からアダプター境界へ分ける。
* `GameOasis.Application`と`Storage`には横断責務だけを残すか、空になれば廃止候補とする。

完了条件：ロビーのカタログ読込・編集・保存がGUIとゲーム実装なしで検査できる。

## 作業段階2：Lobby GUIを物理抽出する

目的：開始前画面と操作を`LobbyGui` ProjectFamilyへ移します。

作業：

* `LobbyGuiController`、表示状態、入力コマンド、ロビー用Presenter／Rendererを移す。
* `Game1`からロビー画面の更新・描画・画面遷移を小さなホストへ委譲する。
* Windows固有のダイアログ、クリップボード、フォルダー表示を`LobbyGui.Windows`へ接続する。
* プレイルーム開始後の型をLobby GUIの公開APIから除く。

完了条件：Lobby GUIプロジェクトがPlay Room具象実装を参照せず、開始要求までを単独検査できる。

## 作業段階3：共通Play Room GUI境界を作る

目的：ゲーム別GUIを抽出できる最小のGUIホスト契約を定めます。

作業：

* 起動要求、状態スナップショット、入力、通知、終了結果のGUI向け境界を確定する。
* MonoGameの共通描画サービスとゲーム固有Presenterを分ける。
* Match、Review、Board Editor、Watchのライフサイクルを共通化し過ぎず分類する。
* 複数GUI接続を今回の要件に含めるか明記する。

完了条件：偽Play Room Engineを使い、GUI境界の開始・入力・更新・終了を画面なしで検査できる。

## 作業段階4：囲碁Play Room GUIを抽出する

目的：盤、着手、棋譜、レビュー、解析表示を`Reference.PlayRoomGui.Go`へ移します。

作業：

* `GoAppSession`を開始前ロビー状態と開始後Play Room状態に分割する。
* Local Match、CGOS観戦、Review、Board Editorの表示状態をPlay Room側へ移す。
* `Game1`を共通ホストと画面実装の構成点まで薄くする。
* SGF、GTP、CGOSのFormalAdapterは公開境界越しに利用する。

完了条件：囲碁Play Room GUIがLobby GUIの内部型を参照せず、保存済み起動要求から開始できる。

## 作業段階5：Play Room Engineを実装単位へ整理する

目的：Protocol S実装を`Reference.PlayRoomEngine.<Implementation>`へ揃えます。

作業：

* 通常囲碁とポン抜きのルール実装、ホスト、マニフェストの所有名を再評価する。
* Board Editor、Review、Match Hostのうち、GUI HostとEngine Hostに分けるべき責務を分類する。
* 共通`PlaySpace.JsonLines` SDKを利用し、独自通信ループを作らない。
* 言語非依存適合性ベクトルを維持する。

完了条件：各EngineがGUI、Lobby、他ゲーム実装なしでProtocol S適合性検査に合格する。

## 作業段階6：実行ホストと発行物を分離する

目的：Lobby GUIとPlay Room GUIを独立起動・更新できる形へ近づけます。

作業：

* `LobbyGui.Windows`とゲーム別Play Room GUI Hostの実行入口を追加する。
* ランチャーのアプリケーション登録、発行先、アイコン、設定引継ぎを更新する。
* 現行Game Oasis GUI実行ファイルを互換入口として残す期間と廃止条件を定める。
* 正常終了、異常終了、子プロセス不在、Protocol版不一致から復帰できるようにする。

完了条件：Lobbyを閉じずにPlay Roomを開始・終了でき、Play Room障害後もLobbyが操作可能である。

## 作業段階7：旧配置と横断領域を仕上げる

目的：移行用の重複と曖昧な所有を除去します。

作業：

* `GameOasis.Gui`に残る型へ横断残置理由を付け、役割固有型を除去する。
* 空になった旧プロジェクト、互換名前空間、重複アダプターを削除する。
* SDK文書、開発者README、ソリューション、発行スクリプトを追随させる。
* 外部仕様型がLobby／Play Roomのカジュアルな内部状態へ漏れていないか検査する。

完了条件：4役とGame Oasis横断領域の所有者がプロジェクト名から判別でき、旧配置に実装の重複がない。

## 検証

各段階で最低限、次を確認します。

* ソリューション全体Releaseビルド。
* LobbyEngine、GameOasis.Contracts、Conciergeの単体試験。
* PlayRoom JSON Linesの正常／異常終了試験。
* Protocol S適合性ランナーの通常囲碁、ポン抜き、外部Counter。
* GUI移植性試験とWindows非対話試験。
* ランチャーからLobbyを起動し、Lobbyから各Play Roomを開始・終了する手動試験。
* 発行物に必要なHost、マニフェスト、契約DLLが含まれること。

WindowsのSmart App Controlが未署名の再生成DLLを`0x800711C7`で拒否した場合は、[`Smart App Controlによる再生成DLLブロック調査.md`](../トラブルシューティング/Smart%20App%20Controlによる再生成DLLブロック調査.md)に従い、コード失敗とOS拒否を分けて記録します。PC再起動を通常の試験手順にはしません。

## 実施原則

* 一度に1つの役割境界だけを物理移動する。
* 責務を分けてから改名する。
* `Game1`または`GoAppSession`を一括移動しない。
* 同一プロセスと別プロセスの両アダプターを同時に全面変更しない。
* 保存形式、実行ファイル互換、ランチャー更新経路を優先する。
* 利用者の指示なしにSmart App Controlを無効化しない。
