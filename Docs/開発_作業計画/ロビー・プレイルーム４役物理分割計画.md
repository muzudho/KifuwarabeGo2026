# ロビー・プレイルーム4役物理分割計画

状態：作業段階2の第1縦切り、作業段階3・4・5完了、作業段階6の第2縦切り完了（2026年8月30日）

## 目的

現在の`KifuwarabeGo2026.GameOasis.*`に残る役割固有コードを、次の4つのProjectFamilyへ段階的に物理分割します。

1. `KifuwarabeGo2026.LobbyGui`：ゲーム開始前の選択、設定、登録、起動操作。
2. `KifuwarabeGo2026.LobbyEngine`：カタログ、永続化、構成、セッション準備。
3. `KifuwarabeGo2026.Reference.PlayRoomGui.*`：ゲーム中、盤面編集、レビュー、観戦の表示と入力。
4. `KifuwarabeGo2026.Reference.PlayRoomEngine.*`：局面、合法手、状態遷移、終局、結果。

`KifuwarabeGo2026.GameOasis`は廃止しません。複数の役割が共有する契約、Conciergeによる調停、構成点、互換実行ホストだけを所有する横断ProjectFamilyとして残します。

## 先行計画との関係

先行する[`ロビーのＧＵＩとエンジン分割計画.md`](./ロビーのＧＵＩとエンジン分割計画.md)では、同一プロセス境界、`ILobbyEngine`、`LobbyGuiController`、Play Room起動契約、JSON Lines Host、Protocol S SDKまでを整備しました。

本計画はその後続です。論理境界を作り直すのではなく、安定した境界に沿ってソース、プロジェクト参照、実行ホスト、発行物を物理的に分けます。

将来構想の[`Lobby・PlayRoom実行ファイル分離移行計画.md`](../開発/ゲームオアシス構想/Lobby・PlayRoom実行ファイル分離移行計画.md)は参考にしますが、既存の保存形式、公開実行ファイル名、ランチャー起動経路を一括変更しません。


物理分割後も、同一プロセス実装とJSON Lines実装を同じ契約の差し替えとして維持します。

## 所有ルール

### `LobbyGui`

* ゲーム、プレイスペース、参加者、ゲームマスター、対局条件の選択と編集。
* 設定画面、エンジン管理、CGOS接続先管理。
* `PlayRoomLaunchRequest`の作成と開始結果の表示。
* 局面の合法性、手番、勝敗を所有しない。

### `LobbyEngine`

* カタログの正本、正規化、保存ユースケース。
* 利用可能な実装の探索とセッション準備。
* GUI型、MonoGame型、ゲーム局面型を所有しない。

### `Reference.PlayRoomGui.<Implementation>`

* ゲーム中、観戦、編集、レビューの表示と入力。
* Protocol GまたはPlay Room公開契約だけで外側と接続する。
* 永続カタログ、外部実装のインストール、ゲームルールの正本を所有しない。

### `Reference.PlayRoomEngine.<Implementation>`

* ゲーム設定の検査、セッション、状態、行動、リビジョン、終局、結果。
* Protocol Sを公開し、GUI、MonoGame、ロビーの保存型を参照しない。

### `GameOasis`

* 4役が共有する公開契約と識別子。
* Protocol G/P/S/M間の調停。
* 移行中または製品全体の構成点。
* 役割固有の画面、保存処理、ゲームルールを恒久的に集積しない。

互換`GameOasis.Gui`の責務表を現配置へ更新しました。Lobby GUI／Engineと囲碁Play Room GUI／Engineの正本は専用プロジェクトにあり、互換GUIには公開実行名を保つMonoGameシェル、構成点、旧`GoAppSession`から公開起動要求へのAdapter、専用Host未移行のBoard Editor／Review／CGOS／Ponnuki経路が残ることを明示しました。これは重複する正本ではなく、既存画面と保存形式を維持する互換境界です。また、独立`EditEntryProfile`へ置換済みで`#if false`に残っていた旧Entry編集描画と未使用enumを削除しました。

移植性試験は、囲碁Engine Assemblyが旧`.LegacyMatch`名前空間を公開しないことを追加検査します。ソリューション全体のReleaseビルドは警告0・エラー0です。GUI移植性、Windows非対話、通常囲碁Protocol S、Lobby Engine、Play Room JSON Lines、通常囲碁・ポン抜き・外部CounterのProtocol S適合性試験はすべて`PASS`しました。

以上により、段階7で扱う旧仮名称、無効な重複スタブ、横断互換シェルの所有理由を整理し、作業段階7を完了しました。計画全体では作業段階2のLobby画面Renderer／ホスト委譲が第1縦切り後の残件です。

## 実施原則

* 一度に1つの役割境界だけを物理移動する。
* 責務を分けてから改名する。
* `Game1`または`GoAppSession`を一括移動しない。
* 同一プロセスと別プロセスの両アダプターを同時に全面変更しない。
* 保存形式、実行ファイル互換、ランチャー更新経路を優先する。
* 利用者の指示なしにSmart App Controlを無効化しない。
