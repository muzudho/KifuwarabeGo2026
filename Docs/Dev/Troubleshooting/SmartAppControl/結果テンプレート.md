# Smart App Control 診断結果テンプレート

## 目的

同じコミット、同じ構成、同じ出力先で、未署名と署名済みの F5 起動結果を比較する。ビルド結果と Smart App Control による OS 拒否を分けて記録する。

自己署名の Authenticode 状態が `Valid` でも、Smart App Control の起動許可は保証されない。署名済みで拒否された場合は、アプリケーション不具合と判定しない。

## 実施手順

1. 対象プロジェクトを `Debug` / `Any CPU` でビルドし、開始時刻を記録する。
2. 対象プロジェクトを Clean して既存の署名済み出力を削除する。
3. `SmartAppControlSigningEnabled=false` を指定して同じ成果物をビルドする。
4. `Save-SmartAppControlDiagnostic.ps1` を `Signing Disabled`、`F5Result Blocked` または `Succeeded` で実行する。
5. 開発用証明書のサムプリントを `KIFUWARABEGO2026_SAC_SIGNING_CERTIFICATE_THUMBPRINT` に設定する。
6. 通常の `Debug` ビルドを行い、ビルド後の自動署名を完了させる。
7. 同じ開始条件で F5 起動し、開始時刻以降の Code Integrity イベントを採取する。
8. `Save-SmartAppControlDiagnostic.ps1` を `Signing Enabled` と実際の `F5Result` で実行する。
9. 2件の JSON について、対象ファイルの SHA-256、Authenticode 状態、3077 イベントを比較する。

## 判定不能とする条件

* 署名あり／なしでコミット、構成、対象プロジェクト、出力先のいずれかが異なる。
* F5 起動の時刻または対象プロセスが記録されておらず、Code Integrity イベントとの対応を確認できない。
* `AuthenticodeStatus` が `Valid` 以外である。
* 署名後に出力ファイルが変更され、署名時のハッシュと起動時のハッシュが一致しない。
* イベントログの取得権限または保存先への書込み権限がない。

## 結論の書き方

* `Valid` の署名済み成果物が 3077 で拒否された場合、自己署名はこの端末の Smart App Control を通過する根拠にならない。
* 3077 がなくアプリケーションが失敗した場合、Smart App Control とは別にアプリケーションの障害として調査する。
* Smart App Control を無効化したりポリシーファイルを変更したりせず、信頼されたプロバイダーの署名、Trusted Signing、または開発用 VM を次の選択肢として記録する。
