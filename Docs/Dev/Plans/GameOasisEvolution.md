# Game Oasisの将来接続・互換方針

v4.0.0構想のうち、長期の設計意図と互換移行方針です。個々のv4.0.0移行段階の最新TODOは[現状一覧](../CurrentState/Architecture.md)から後続計画を確認します。

## 将来の言語非依存接続

v4.0.0の現在段階では、ContractsのC#インターフェースとC#参照実装を先に完成させます。これは最終的にGame Oasisへの参加をC#へ限定するという意味ではありません。

将来は、次のすべてを実装言語や実行環境を問わず接続できるようにします。

- プレイヤーエンジン（Protocol P）
- ゲームマスターエンジン（Protocol M）
- GUIエンジン（Protocol G）
- プレイスペースエンジン（Protocol S）

C#版で要求、応答、通知、エラー、ライフサイクル、リビジョン、能力情報の意味を十分に検証した後、その意味契約をテキストベースの言語非依存仕様へ写します。標準入出力、ソケット、JSON Lines、メッセージID、非同期通知、プロセス起動・終了、タイムアウト、文字コードなどの配送仕様は、その段階で整理します。

現時点ではテキスト形式や配送方式を確定しません。先に形式を固定してC#概念モデルを歪めたり、C#型名やアセンブリ名を外部仕様へ露出させたりしないためです。`ContractDocument`、安定識別子、Protocol P・M・G・Sの境界は、将来の直列化を妨げない粒度に保ちます。

## 互換性と移行時の注意

### v4.x.xを移行期間とする方針

v4.0.0から最後のv4系リリースまでの`v4.x.x`全体を、v3系から新しいGame Oasis構成へ移るための互換移行期間とします。v4ではプロジェクト、名前空間、内部参照、実行時の所有境界を破壊的に再構成しますが、v3利用者が使用している配布物、ランチャー、設定、保存データ、登録済みエンジンに対しては、移行手段を用意せずに互換経路を削除しません。

この方針における「v4.0.0の破壊的変更」は、主としてソースコードと内部アセンブリ構成に対するものです。利用者向けの実行ファイル名、Release資産名、保存形式、設定項目、標準入出力プロトコルは、v4系の途中で新名称または新形式を導入する場合も、v3互換名、読み込み経路、変換アダプターのいずれかを併設します。

| 互換対象 | v4.x.xで維持する方針 |
|---|---|
| v3ランチャー | v3ランチャーが認識するGUI版・Engine版のRelease資産名とSHA-256資産を公開し続け、v4の互換パッケージを取得できるようにする |
| ランチャーの操作 | `GUI UPDATE`と`ENGINE UPDATE`を移行期間中は有効に保つ。新しい概念名を表示する場合も、旧操作から同等の更新経路へ到達できるようにする |
| GUI／コンシェルジュ実行ファイル | 新しい`Concierge`名を導入する場合、旧GUI実行ファイル名を起動用の薄い互換ホストまたはランチャー側の別名解決として維持する |
| 公式Engine実行ファイル | 新しい`PlayerEngine`名を導入する場合も、`KifuwarabeGo2026.Engine.exe`で起動する既存設定、GTP利用者、CGOS連携のための互換ホストを維持する |
| ゲームスペース | 独立実行ファイル版を追加しても、現行の同一プロセス内プレイスペース経路を、対応する移行経路と検証が完成する前に削除しない |
| 利用者設定とカタログ | v3の設定、エンジンプロファイル、エントリー、接続設定を読み込み、新形式へ移す場合は元データを保持して再実行可能な移行にする |
| 棋譜と保存データ | v3で保存したSGFその他の公開済み形式を読み込めるようにし、新形式だけへ一方的に切り替えない |
| 標準入出力通信 | 公開済みGTP経路を維持し、Protocol P・Sなどの新しいテキストプロトコルへ接続する場合はアダプターを介して段階移行する |
| ロールバック | v4版の導入後も、ランチャーが保持する直前の正常なv3／v4パッケージへ戻せる構成を保つ |

ランチャーの最終的な責務はコンシェルジュのインストール、更新、起動、復旧とし、ゲームスペースとプレイヤーエンジンの登録・更新はコンシェルジュへ移します。ただしv4.x.xでは、既存の`GUI UPDATE`と`ENGINE UPDATE`を直ちに削除せず、新しい更新経路が実運用で安定し、旧経路からの移行とロールバックを検証できるまで併設します。

v3互換経路の廃止はv4.x.xでは行いません。廃止を検討できる最も早い製品世代をv5.0.0とし、その場合も対象、代替手段、データ移行方法、告知期間を別の移行計画で明示します。したがって、v4系のマイナー版またはパッチ版への更新によって、v3から継続利用している環境が突然起動不能になる変更は許容しません。

- v3系のGTPコマンドや設定ファイルを、プロジェクト名変更だけを理由に同時廃止しません。
- プロトコルP、M、G、Sのバージョンは、製品バージョンと分けて管理できる設計にします。
- 外部実装が利用するContractsは、破壊的変更の判定と移行ガイドを提供できる形にします。
- 保存済みSGF、エンジンプロファイル、CGOS接続設定、利用者設定の互換性を個別に確認します。
- v3とv4の型を一時的に変換するアダプターを許容します。
- 名前空間変更とファイル移動を同じコミットに詰め込みすぎず、レビュー可能な単位に分けます。
