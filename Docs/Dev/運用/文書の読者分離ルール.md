# 文書の読者分離ルール

利用者が読みたい説明と、開発者が必要とする内部情報を混在させないための執筆ルールです。

## 文書の配置

- `Docs/Dev/` — 開発者向け文書の入口。
- `Docs/Dev/CurrentState/` — 実装状況、現在の構成、採用仕様、検証結果。確認日・対象版・未確認範囲を記す。
- `Docs/Dev/Plans/` — 将来構想、未実施の作業、検証待ち。現状説明と相互リンクする。
- `Docs/Dev/Archive/` — 置換済みの案、過去の調査・引き継ぎ。当時の「現在」「次回」を現在の指示と扱わない。
- SDK、運用手順、参考資料、完了記録は目的別の配置を維持する。混在する文書は節・項目単位で分け、移動・新規作成するパスは英語にする。
- `Docs/Dev/Log/YYYY/MM.md` — 年別・月別の開発日誌。例: `Docs/Dev/Log/2026/07.md`。
- `Docs/User/` — ユーザー向けの操作説明など。
- `Docs/【むずでょ個人用】/` — 個人用メモ。

文書全体の入口は [Docs/README.md](../../README.md)、開発者向けの目次は [Docs/Dev/README.md](../README.md) です。既存の公開文書は `PublicDocs/` にあります。

## トップREADME

リポジトリ直下の `README.md` は、開発環境を持たず、配布ZIPを展開してexeをダブルクリックする利用者向けに書きます。

優先して記載する内容:

- 何ができるアプリケーションか
- スクリーンショット
- Windowsでの動作環境
- リリースページからのダウンロード方法
- ZIPの展開方法
- exeの起動方法
- GUI版とEngine版の違い
- 利用者から見た主な機能
- 利用時の注意

トップREADMEへ原則として記載しない内容:

- SDKのインストール
- `dotnet build`、`dotnet run`、`dotnet publish`
- プロジェクトやアセンブリの内部構成
- テストプロジェクトの実行方法
- CI、移植、依存関係の実装詳細
- 開発途中の調査記録

開発者向け情報への入口として、`README.developer.md` への短いリンクを置きます。

## 開発者向けREADME

リポジトリ直下の `README.developer.md` は、ソースコードを取得してビルド、テスト、改造、移植、リリースする人向けに書きます。

次の内容を扱います。

- 必要なSDKと開発環境
- ソリューションとプロジェクトの構成
- ビルドと開発実行
- 自動テストと手動テスト
- publishとリリース手順
- 設計文書、開発日誌、引き継ぎ文書へのリンク

## 開発日誌

開発日誌へ機能追加やリリースを記録するときは、可能な限り次の2つを分けます。

### ユーザー向けの説明

- 利用者に何ができるようになったか
- 以前より何が簡単・安全・分かりやすくなったか
- 画面上のボタン名や操作方法
- 利用者が知る必要のある互換性や注意点

内部クラス名や実装方式を知らなくても読める文章にします。

### 開発者向けの説明

- 主な実装場所
- 共通化した部品や状態管理
- データ形式と互換処理
- 回帰検査
- ビルド、publish、配布物の確認結果
- 将来の拡張や未解決事項

## リリースノート

GitHub Releaseへ掲載するリリースノートは、最初にユーザー向けの変更を記載します。

内部実装や検査結果は「開発者向け」「技術情報」「テスト状況」などの別節へ分けます。リリースの主役は、クラス名やプロジェクト構成ではなく、利用者が得る改善です。

## 書き分けの判断

迷った場合は、次の質問で判断します。

> Visual Studioやソースコードを持たず、exeをダブルクリックして使う人が、この情報を必要とするか。

- 必要なら利用者向け。
- 不要なら開発者向け。
- 両方に必要なら、利用者向けには結果と操作を、開発者向けには理由と実装を記載します。
