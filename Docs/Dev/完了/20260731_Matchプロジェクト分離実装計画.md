# Matchプロジェクト分離実装計画

作成日: 2026-07-31

整理状態: 完了（ファイル名の日付は開始日）

## 完成条件

`KifuwarabeGo2026.Match` が、画面や通信方式を知らずに一局の対局を進行できる状態を完成とする。

- `net8.0` クラスライブラリである。
- 参照する自作プロジェクトは `KifuwarabeGo2026.Shared` だけである。
- MonoGame、Windows API、HTTP、WebSocket、GTPプロセスを参照しない。
- 人間同士のローカル対局を、GUIからMatchのAPIを通して開始・進行・終了できる。
- 将来のWebサーバーが同じAPIを呼べる。
- 既存のGUI操作と棋譜結果を壊さない。

## 責務の境界

```text
Windows GUI
  ├─ クリック、描画、効果音、画面遷移
  ├─ GTPエンジンアダプター
  └─ Match APIの呼び出し
             │
             v
KifuwarabeGo2026.Match
  ├─ 対局状態
  ├─ 着手、パス、投了
  ├─ 手番交代、コウ、終局
  └─ 状態スナップショットと結果
             │
             v
KifuwarabeGo2026.Shared
  └─ 盤、石、座標などの基本型

将来のWebサーバー
  ├─ ログイン、権限、接続、再接続
  ├─ HTTP、WebSocket、永続化
  └─ Match APIをラッピング
```

## 最小APIのたたき台

名前は実装時に既存コードとの整合を確認して確定する。

```csharp
public sealed class MatchSession
{
    public MatchSnapshot Snapshot { get; }

    public MatchActionResult Play(GoPoint point);
    public MatchActionResult Pass();
    public MatchActionResult Resign();
}
```

設計上の原則は次のとおり。

- 呼び出し元が現在の手番を偽装しなくてよいよう、最初はセッション自身が手番を管理する。
- APIへMonoGameの `Point` を渡さず、Sharedの `GoPoint` を使う。
- 成功・失敗を単なる `bool` にせず、失敗理由と更新後状態を返せる結果型にする。
- 表示用文字列ではなく、合法手違反、コウ、終局済みなどを列挙値で表す。
- 状態はGUIが自由に書き換えず、コマンドの結果として更新する。
- サーバー固有の利用者ID、ソケット、認証情報をAPIへ持ち込まない。

## 第2段階：対局状態とコマンド結果を作る

状態: 2026-07-31 実装完了。GUIへの接続は第3段階で行う。

### 作業

- `MatchSession`、`MatchSnapshot`、`MatchActionResult` を追加する。
- 手番、盤面、コウ、連続パス、進行中・終局済みの状態を保持する。
- 着手、パス、投了を実装する。
- Sharedの `GoBoard`、`GoStone`、`GoPoint` を利用する。
- 純粋なライブラリテストまたは移植性スモークで基本遷移を検査する。

### 最初に検査するケース

- 黒から開始し、合法手後に白へ手番が移る。
- occupied、盤外、コウなどの不正着手で状態が変わらない。
- パスで手番が移る。
- 連続2回のパスで現在と同じ終局処理になる。
- 投了した側と勝者を識別できる。
- 終局後の着手を拒否する。

### 実施結果

- `MatchSession` を追加し、盤面、手番、単純コウ、連続パス、着手数、リビジョン、終局理由、勝者をMatch側で管理するようにした。
- `MatchSnapshot` を追加し、盤面を含む変更不能な時点状態を返すようにした。
- `MatchActionResult` と失敗理由を追加し、盤外、占有点、単純コウ、その他の不正着手、終局後操作を区別した。
- 着手、パス、投了を実装した。連続2回のパスでは終局理由を返し、採点と勝者決定は後続段階へ残した。
- 盤外、占有点、自殺手、スナップショット不変性、連続パス、投了、終局後拒否、単純コウを移植性スモークで検査した。
- GUIはまだMatch APIを呼んでいない。

## 第3段階：人間同士のGUI対局をMatchへ接続する

状態: 2026-07-31 実装完了。通常開始の人間同士対局だけを対象とする。

### 作業

- `GoAppSession.TryPlaceStone`、`Pass`、`Resign` の対局中核をMatchへ委譲する。
- GUIのクリック判定、効果音、画面遷移はGUI側に残す。
- Matchのスナップショットから既存描画に必要な状態を供給する。
- Matchの結果から既存の棋譜と結果画面を更新する。
- 移行中は旧状態との二重管理を最小限にし、Matchを正本にする時点を明記する。

### 完了確認

- 既存の手動スモーク「ラウンドA」が通る。
- 人間同士で着手、パス、投了、結果画面、タイトル復帰ができる。
- GUIがMatch内部状態を直接変更していない。

### 実施結果

- 通常開始、黒白ともHuman、空の初期盤面という条件で `MatchSession` を生成するようにした。
- GUIの着手、パス、投了をMatchへ委譲し、返された変更不能スナップショットから表示用盤面、手番、コウ、連続パス、着手数を同期する。
- GUIの棋譜、アゲハマ、結果画面は既存形式を維持した。
- パス・パスと手数上限では、Matchは勝敗を決めず `AwaitingResult` へ進む。
- 現行ローカルGUIだけは互換性のため、`AwaitingResult` を受けて既存の純碁簡易採点を行う。この処理はMatchの外側にある。
- 盤面編集局面からの開始、人間対コンピューター、コンピューター同士はまだ従来経路を使う。
- GUI接続回帰を移植性スモークへ追加し、着手、盤面・手番同期、棋譜追加、パス・パス、投了を検査した。

## 第7段階：結果合意API

状態: 2026-07-31 実装完了。Webサーバー側の認証・権限確認とGUI画面は将来段階とする。

結果確定を次のモデルで実装する。

- パス・パスまたは手数上限で `AwaitingResult` へ進む。
- 黒白プレイヤーが勝者、得点、無勝負などの結果を申告する。
- 双方の申告が一致したら `Completed` へ進む。
- 不一致なら結果待ちを続け、対局再開または審判裁定を受け付ける。
- 審判裁定には、サーバー側で権限確認済みの命令だけを渡す。
- Matchやサーバーが盤面だけから日本ルールの勝者を推測しない。

### 実施結果

- `MatchOutcome` と `MatchResult` を追加し、黒勝ち、白勝ち、持碁、無勝負と任意の勝差を構造化した。
- 持碁と無勝負へ勝差を指定すること、および0以下の勝差を拒否する。
- `DeclareResult` を追加し、黒白それぞれの申告をスナップショットへ保持する。
- 同一プレイヤーによる同じ申告の再送は、成功扱いのまま状態とリビジョンを変更しない。
- 片方だけ、または申告不一致では `AwaitingResult` を維持する。
- 黒白の申告が一致すると、確定結果と勝者を設定して `Completed` へ進む。
- `ResumePlay` を追加し、申告を消去して対局を再開できるようにした。
- `ApplyAdjudicatedResult` を追加し、審判が黒勝ち、白勝ち、持碁、無勝負を確定できるようにした。
- 投了時も `ConfirmedResult` に構造化された相手勝ちを設定する。
- 結果申告、合意、対局再開、審判裁定をMatchイベントへ追加した。
- 最初の申告、冪等再送、不一致、再申告による一致、対局再開、無勝負裁定、不正勝差、各観戦イベントを移植性スモークへ追加した。

## 第5段階：GTPプレイヤーを外から接続する

状態: 2026-07-31 実装完了。任意編集局面に対する外部エンジン互換性には既知の制限がある。

### 作業

- `PlayingScene` のGTP制御を、Matchの状態を読みコマンドを発行するアダプターとして整理する。
- GTPの着手応答を、Matchの `Play` または `Pass` へ入力する。
- MatchからGTPプロセスを直接起動しない。
- エラー表示、ログ、プロファイル保存はGUI側へ残す。

### 完了確認

- 人間対コンピューターとコンピューター同士が従来どおり動く。
- 編集局面からコンピューター同士で開始する既知のエラーも回帰対象に含める。
- GTPがなくてもMatch単独のテストが動く。

### 実施結果

- 人間対コンピューターとコンピューター同士を含む、すべてのローカル対局で `MatchSession` を生成するようにした。
- GTPから返った着手、パスは既存 `GoAppSession` 経由でMatchへ入力され、Matchの操作履歴へ残る。
- `GtpInitialPositionCommandBuilder` をGUI側へ追加し、MatchスナップショットをGTP初期化コマンド列へ変換するようにした。
- 従来は編集盤面を `clear_board` 後にエンジンへ送っていなかった。現在は黒白の初期配置石を `play` コマンドで同期する。
- MatchはGTP名前空間、外部プロセス、ログ、エンジン設定を参照しない。
- コンピューター同士のMatch接続、エンジン着手のMatch履歴追加、初期配置コマンドの順序と座標を移植性スモークへ追加した。
- 同梱GTPエンジンへ9路、コミ6.5、黒A9、白J1の初期化コマンド列を送り、すべて成功応答することを確認した。
- 任意の編集局面を標準GTPだけで完全に設定する方法はないため、外部エンジンが `play` による初期配置を拒否する場合はエラーになる。この場合の `loadsgf` などは将来の能力別アダプター候補とする。

## 第6段階：時計と観戦向けイベントを追加する

状態: 2026-07-31 実装完了。サーバーホスト、通信、永続化は将来段階とする。

### 作業

- Web対局の時計はサーバー側を正本とし、クライアント自己申告の経過時間を採用しない。
- サーバー側の信頼できる時計サービスが着手受理時刻、残り時間、期限、時間切れを決定する。
- クライアントへ手番ごとの時刻情報を送り、クライアントは次の同期まで表示だけを補間する。
- Matchへ時計状態を持たせる場合は、サーバー側が決定した更新だけを受け付ける決定論的APIにする。
- 状態変更イベントまたは連番付きスナップショットを定義する。
- ローカルGUIと将来のWeb観戦で同じ意味になるデータだけをMatchから公開する。
- 切断、再接続、配送保証はサーバー側の責務としてMatchへ入れない。

### 完了確認

- 同じコマンド列から同じ対局状態を再現できる。
- WebサーバーがMatchをラッピングする際、GUI型やWindows型が不要である。

### 実施結果

- `MatchClockUpdate` と `MatchClockSnapshot` を追加した。
- 時計更新はサーバーが決定した同期時刻、黒白の残り時間、手番期限、単調増加シーケンスを完全スナップショットとして受け付ける。
- Matchは現在時刻を取得せず、クライアント自己申告の経過時間を加算するAPIを持たない。
- 同じまたは古い時計シーケンスを拒否し、時計状態とMatchリビジョンを変更しない。
- 負の残り時間を拒否する。
- 時計同期はMatchリビジョンを進めるが、着手数へ数えない。
- `MatchEventRecord` と `MatchEventKind` を追加し、受理済み操作と時計同期を通信非依存イベントとして保持する。
- `GetEventsAfter(revision)` を追加し、観戦・再接続側が既知リビジョン以降の差分だけ取得できるようにした。
- 時計同期、古い同期拒否、負時間拒否、時計後の着手リビジョン、全イベント取得、差分取得を移植性スモークへ追加した。
- MatchはHTTP、WebSocket、認証、観戦者一覧、ファイル、データベースを参照しない。

## 実装中に守ること

- 大きな一括移動を避け、一段階ごとにビルドとスモークを通す。
- MatchからGUIへの逆参照を作らない。
- Matchの公開APIへファイルパス、表示文言、通信オブジェクトを混ぜない。
- 既存挙動を意図せず変更しない。ルール変更は分離作業とは別に扱う。
- 移行用の互換コードには、削除条件を文書またはコメントで残す。
