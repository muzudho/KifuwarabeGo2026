# Go Apps共通規約

> 対応バージョン：KifuwarabeGo2026 v3.3.0<br>
> 記事の更新日：2026-08-02

## 最初から順に実装する

Go Apps対応エンジンは、次の順序で一段ずつ動作確認できます。

### 1. GTP応答を返す

標準入力から一行ずつコマンドを読み、成功時は`=`、失敗時は`?`で始まる応答と末尾の空行を返します。

### 2. エンジン自身を説明する

`protocol_version`、`name`、`version`を実装し、単体起動したエンジンへ一つずつ送って応答を確認します。

### 3. 対応コマンドを公開する

`known_command <command-name>`と`list_commands`を実装します。`known_command`が`true`を返す名前と、`list_commands`へ掲載する名前を一致させます。

### 4. 対応するGo Appを公開する

`kfw-list-apps [player|provider]`を実装します。roleを指定した場合はそのroleで対応するアプリIDを、引数なしの場合は全roleの和集合を、一行に一つずつ返します。

```text
> known_command kfw-list-apps
= true

> kfw-list-apps
= play
ponnuki

> kfw-list-apps player
= play
ponnuki

> kfw-list-apps provider
= ponnuki

```

`kfw-list-apps`自身も`list_commands`へ掲載します。未知のroleや余分な引数を受け取った場合は、GTPエラーを返します。

```text
> kfw-list-apps spectator
? usage: kfw-list-apps [player|provider]

```

ここで返すのはアプリIDだけです。同じroleで同じアプリIDを重複して返してはいけません。引数なしの応答でも、複数roleに対応する同じアプリIDは一度だけ返します。

### 5. roleを一つ選んで実装する

アプリIDをrole別に公開した後、そのアプリのPlayerまたはProviderに必要なコマンドを実装します。`kfw-list-apps <role>`は対応表明であり、実際にそのroleとして成立するには次の必須コマンド群も必要です。

| app-idとrole | 次に確認する主なコマンド |
|---|---|
| `play player` | `boardsize`、`clear_board`、`komi`、`play`、`genmove` |
| `ponnuki provider` | `kfw-make-position`、`kfw-listen-move` |
| `ponnuki player` | 原子的指定局面6コマンド、`play`、`genmove` |

一つの実行ファイルが複数のapp-idやroleへ対応しても構いません。実装するroleごとに、リンク先の実装確認表を上から順に確認してください。

## 1. アプリID

アプリIDは、相互運用するアプリの種類を表すlower camel caseの識別子です。先頭を小文字にし、複数単語の場合は2語目以降の先頭を大文字にします。PascalCaseは使用しません。

```text
play
ponnuki
captureGo
```

アプリIDへエンジン名、作者名、プロトコル名を接頭辞として付けません。例えば、ポン抜きのアプリIDは`ponnuki`であり、`kfw-ponnuki`ではありません。

> **引用用要件：アプリID**  
> アプリIDは特定実装の所有者を表さず、相互運用するアプリの種類を表す。同じアプリIDを名乗る実装は、そのIDで普及しているプロトコルとの互換性を維持しなければならない。

## 2. エンジンの役割

Go Appsでは、アプリIDに加えてエンジンの役割を区別します。

| 役割 | 識別子 | 主な責務 |
|---|---|---|
| Player | `player` | 盤面を受け取り、次の着手を生成する |
| Provider | `provider` | 初期局面の生成、着手の監視、アプリ固有の終局判定を行う |

対象用途は、`ponnuki player`、`ponnuki provider`のように「アプリIDと役割」の組で表します。

> **引用用要件：役割**  
> PlayerとProviderは独立した役割である。Playerは着手生成を担当し、Providerはアプリ固有の局面や進行判定を担当する。一つのエンジンが両方へ対応することは必須ではない。

## 3. 通信方式

Go Appsのエンジンは、標準入力でコマンドを受け取り、標準出力へGTP形式の応答を返します。

成功応答は`=`、失敗応答は`?`で始め、最後に空行を出力します。

```text
= response body

? error message

```

JSONを返すコマンドでも、JSONだけを出力するのではなく、GTP成功応答の本文として出力します。診断メッセージを標準出力へ混入させることは禁止します。ログが必要な場合は標準エラーなど、GTP応答を壊さない出力先を使用します。

## 4. 能力確認

エンジンはGTP Version 2の`known_command`と`list_commands`へ正しく応答してください。対応するKFW拡張コマンドは`list_commands`へ含め、`known_command <command-name>`へ`true`を返します。

```text
> known_command kfw-make-position
= true

> known_command kfw-listen-move
= true
```

未対応のコマンドを受け取った場合は、成功したように見せずGTPエラーを返してください。

エンジンがrole別に対応するGo Appの一覧は、`kfw-list-apps player`または`kfw-list-apps provider`で問い合わせます。引数なしでは全roleの和集合を返します。`play`は通常の囲碁対局を表す共通アプリIDです。実装手順と単体確認例は、冒頭の［対応するGo Appを公開する］を参照してください。

```text
> kfw-list-apps player
= play
ponnuki

```

GUIは`known_command kfw-list-apps`で対応を確認した後、画面側で必要なroleを指定して一覧を取得します。v3.2.0エンジンがrole引数をエラーにした場合は、互換のため引数なしの一覧へフォールバックします。この場合はアプリ対応だけを確認でき、role対応は未確認として表示します。

GUIのエンジン選択では、次の互換規則を使用します。

| 状態 | `play`での扱い | その他のGo Appでの扱い |
|---|---|---|
| `kfw-list-apps`未実装 | `play player`だけ従来型として選択可能 | 選択不可 |
| role指定へ対応し、対象アプリIDを返す | 選択可能 | 選択可能 |
| role指定は未対応だが、引数なしで対象アプリIDを返す | role未確認として選択可能 | role未確認として選択可能 |
| 実装済みで対象アプリIDを返さない | 選択不可 | 選択不可 |
| 能力照会がエラー、タイムアウト、不正応答 | 選択不可 | 選択不可 |

選択不可のエンジンも登録一覧には表示し、非対応または確認失敗の理由を表示します。これにより、従来のGTPエンジンとの互換性を維持しつつ、新しいエンジンが公開した対応範囲を尊重します。

> **引用用要件：能力確認**  
> エンジンは対応する拡張コマンドを`list_commands`で公開し、`known_command`へ正しく回答しなければならない。GUIはコマンドを使用する前に能力を確認する。

## 5. コマンド名

KifuwarabeGo2026で提案された独自GTP拡張は、標準GTPコマンドと区別するため`kfw-`接頭辞とkebab-caseを使用します。

```text
kfw-make-position
kfw-listen-move
kfw-list-apps
kfw-describe-options
kfw-get-options
kfw-patch-options
kfw-invoke-option
kfw-begin-position
kfw-add-black
kfw-add-white
kfw-set-to-play
kfw-commit-position
kfw-abort-position
```

`kfw-`はプロトコルの名前空間です。第三者のエンジンも、同じ意味と応答形式を実装する場合は同じコマンド名を使用できます。

## 6. エラー処理

引数の個数、アプリID、バージョン、座標、値が不正な場合、エンジンは理由を含むGTPエラーを返します。不正な要求を黙って受理したり、成功応答の中にエラーを埋め込んだりしてはいけません。

GUIが処理を継続できるよう、エラーが起きたコマンドで盤面や進行状態を途中まで変更しない設計を推奨します。指定局面の受け渡しでは、[ポン抜きPlayer](Ponnuki/Player.md)に記載する原子的指定局面コマンドを使用します。
