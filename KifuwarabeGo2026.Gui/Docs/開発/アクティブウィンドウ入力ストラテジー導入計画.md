# アクティブウィンドウ入力ストラテジー導入計画

## ウィンドウスタック

`ActiveWindowId` を一つだけ保持するのではなく、モーダル画面を開いた順に `ActiveWindowStack` へ積みます。入力先は常にスタック最上位です。

```text
PLAYER SELECT を開く       [PlayerSelection]
SELECT ENGINE を開く        [PlayerSelection, GtpEngineSelection]
ENGINE を閉じる             [PlayerSelection]
PLAYER SELECT を閉じる      []
```

子画面を閉じると親画面の入力先が自然に復帰し、背面の画面へクリックが流れません。

### 最初の実装対象

最初は `PlayerSelection` と `GtpEngineSelection` / `GtpEngineEdit` をスタック管理へ移行します。`Game1.UpdateMouseInput` はスタック最上位のハンドラを先に呼び、処理済みなら直ちに return します。以後は Client Identity、Tournament Rules、各種テキスト入力モーダルを同じ方式へ段階的に移します。

## 背景

画面上にダイアログを重ねて表示する場合、背後のダイアログの状態を保持したまま、前面のダイアログを開くことがある。

2026-08-12 に、CGOS の PLAYER SELECT を背後に残したまま SELECT ENGINE (GTP) を表示した際、`Game1.UpdateMouseInput` が PLAYER SELECT を先に判定し、前面の GTP ダイアログがクリックを受け取れない問題が発生した。

当面の修正として、CGOS のクリック処理でも GTP 編集・選択ダイアログを PLAYER SELECT より先に判定するようにした。しかし、個別の `if` の並び順で前後関係を維持する方式では、新しいダイアログを追加するたびに同種の漏れが起こり得る。

## 目標

表示上の最前面にある「アクティブウィンドウ」だけが入力を受け取る仕組みにする。

- 背後の画面・ダイアログは描画を続けても、クリック・ドラッグ・キー入力を受け取らない。
- 入力の優先順位を `Game1.UpdateMouseInput` の条件分岐に分散させない。
- 新しいダイアログは、アクティブウィンドウ ID と対応する入力ストラテジーを登録するだけで追加できる。
- モーダルではない盤面操作や常設操作は、アクティブウィンドウが無い場合だけ入力を受け取る。

## 設計案

### 1. アクティブウィンドウを明示する

`ActiveWindowId`（仮称）を定義する。例:

```csharp
public enum ActiveWindowId
{
    None,
    GtpEngineSelection,
    GtpEngineEdit,
    PlayerSelection,
    PlayerEdit,
    ClientIdentitySelection,
    ClientIdentityEdit,
    TournamentRulesSelection,
    TournamentRulesEdit,
    CgosAdminPlayerSelection,
    TextInput,
    IntegerInput,
    CommentEditor,
    ReviewUnsavedChangesConfirmation,
}
```

`GoAppSession` の既存フラグ群から毎フレーム最前面の ID を導出する方式、または `Open...` / `Close...` がスタックを操作する方式を採用する。ネストしたダイアログを正しく戻せるため、後者のウィンドウスタック方式を基本案とする。

### 2. 入力ストラテジーをウィンドウごとに持つ

クリック・ドラッグ・キー入力を扱う共通インターフェースを設ける。

```csharp
internal interface IActiveWindowInputStrategy
{
    ActiveWindowId WindowId { get; }
    bool HandleClick(Point point);
    void HandleDrag(MouseState mouse, Point point);
    void HandleKeyboard(KeyboardState keyboard, GameTime gameTime);
}
```

実装は GTP エンジン選択、PLAYER SELECT、各テキスト入力など、現在 `Game1` に散在する `TryHandle...` 単位を薄くラップして始める。画面固有の状態変更は `GoAppSession` に残し、ストラテジーは入力の振り分けだけを担当する。

### 3. 単一のディスパッチ地点を作る

`Game1.UpdateMouseInput` のクリック検出後、最初にアクティブウィンドウを取得して対応ストラテジーへ渡す。

```csharp
if (_activeWindowInputDispatcher.TryHandleClick(point))
{
    _previousMouse = mouse;
    return;
}
```

アクティブウィンドウがある場合、未命中のクリックも背後へ流さない。これにより、モーダルの外側クリックを無視する仕様も一貫する。

### 4. 描画順と入力順を同じ情報源にする

描画も `ActiveWindowId` / ウィンドウスタックの上から順に行う。これで「表示は前面だが入力は背後」という不整合を防ぐ。

StickyNote はアクティブウィンドウとは別概念とする。現在の StickyNote 表示位置ストラテジーは、パンくずに対応する画面 ID と紐づいており、モーダル表示中に出さない既存ルールを維持する。

## 移行手順

1. `ActiveWindowId` とウィンドウスタックを追加し、既存の GTP エンジン選択だけを登録する。
2. CGOS の PLAYER SELECT → GTP 選択のネストを手動確認し、背後の PLAYER SELECT が入力を受けないことを確認する。
3. PLAYER SELECT / PLAYER EDIT / Client Identity / Tournament Rules を順に移す。
4. PopupTextBox、PopupNumberBox、コメント編集、確認ダイアログを移す。
5. `Game1.UpdateMouseInput` に残るダイアログ専用の優先順分岐を削除する。
6. ダイアログの表示・閉鎖・ネスト復帰の手動スモークテストを追加する。

## 受け入れ条件

- 前面ダイアログを開いている間、背後の画面・ダイアログの操作が一切実行されない。
- ネストしたダイアログを閉じると、直前のダイアログが再びアクティブになる。
- 新規ダイアログ追加時、`Game1.UpdateMouseInput` の大きな条件分岐へ優先順を追記しなくてよい。
- CGOS の PLAYER SELECT から GTP エンジンを選択・編集・キャンセルできる。
- 既存のローカル対局、CGOS、ポン抜きのモーダル操作が維持される。

## 現在の暫定対応

`Game1.UpdateMouseInput` の CGOS 分岐で、GTP エンジン選択・編集のクリック処理を PLAYER SELECT より先に実行するよう修正済み。この修正は動作を復旧するための措置であり、本計画の完了後はアクティブウィンドウ・ディスパッチへ置き換える。
