# UI 操作スタイル方針

## 目的

画面ごとに似た操作が別の意味に見えないよう、ボタンの文言、並び順、保存完了後の遷移をアプリ全体でそろえる。
利用者が編集画面を開いたときは、変更を捨てる操作と、保存して画面を閉じる操作をひと目で区別できることを目標にする。

## 編集画面の標準

変更を下書きとして編集する画面では、右上（または画面の操作列）の左から次の順に置く。

| 左ボタン | 右ボタン |
| --- | --- |
| `DISCARD` | `SAVE & CLOSE` |

- `DISCARD`: 下書きの未保存変更を破棄し、編集画面を閉じる。保存処理は行わない。
- `SAVE & CLOSE`: 入力を検証して保存し、保存が成功したことを確認してから編集画面を閉じる。検証または保存に失敗した場合は画面を閉じず、原因を表示する。
- 保存に時間がかかる操作では、保存中スピナーを表示して二重操作を防ぐ。
- ラベルが長くなる場合も、文字を極端に縮小しない。必要ならボタン幅を広げ、左の `DISCARD` との間隔を保つ。

対象は、プレイヤー、クライアント ID、GTP エンジン、CGOS 接続先、大会ルール、並び順、棋譜コメントなどの編集画面である。

## `CANCEL` を使う場面

`CANCEL` は、保存対象の下書きを破棄する意味を持たない画面だけに使う。

- 選択画面を一つ前へ戻る。
- ファイル選択や候補選択を取り消す。
- 確認ダイアログで「実行しない」を選ぶ。

候補を選んで確定する操作は `SELECT`、設定を適用するだけで閉じない操作は `APPLY`、接続開始など個別の行為は `USE` / `CONNECT` のように、結果が分かる動詞を使う。

## 導入・確認の手順

新しい編集画面を追加するときは、次を満たすことをレビュー項目にする。

1. 変更は保存まで下書きに留まり、`DISCARD` で元に戻る。
2. `SAVE & CLOSE` は保存成功時だけ閉じる。
3. 失敗時は編集内容を残し、理由を表示する。
4. 左に `DISCARD`、右に `SAVE & CLOSE` を配置し、ほかの編集画面と同じ見た目にする。

既存画面は、保存処理と画面を閉じる処理の対応を確認しながら、この標準へ順次移行する。
