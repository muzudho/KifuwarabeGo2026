# ローカル対局と将来の囲碁サーバー共通化方針

## 将来像

- 将来、Web上でログイン、対局、観戦ができる囲碁サーバーを構築する。
- WebサーバーのホストOSはUbuntuを想定する。
- 囲碁サーバーの中核部分はWindowsへ依存させない。

## 基本方針

- 現在GUI内にある「ローカル対局」の中核処理を、`KifuwarabeGo2026.Match` プロジェクトへ分離する。
- ローカルPC版とWeb版で、対局の開始、着手、投了、状態取得、観戦などの同じアプリケーションAPIを利用できる形を目指す。
- ローカルPC版は同一プロセス内のAPI呼び出し、またはローカル用アダプターを通して利用する。
- Web版はHTTP、WebSocket、認証、永続化などの接続部分で中核APIを包む。
- 対局ルールと状態遷移を通信プロトコルへ直接結び付けない。
- GUI、Windows API、MonoGame、ファイルダイアログ、レジストリなどへの依存を `KifuwarabeGo2026.Match` に持ち込まない。

## 境界の考え方

`KifuwarabeGo2026.Match` はサーバーや画面ではなく、対局を表すOS非依存の.NETライブラリとする。外側に実行環境別の入口を置く。

Match自身は待受ポート、HTTP、WebSocket、ログイン、接続管理などのサーバー機能を持たない。将来のWebサーバーがMatchをラッピングし、外部から届いた要求をMatchのAPI呼び出しへ変換する。

## 対局時計の正本

- Web対局の時計はサーバー側が正本を持つ。
- クライアントから自己申告された消費時間は、改ざんできるため正本にしない。
- サーバーは着手を受理した時刻と、次の手番の残り時間または期限を決定する。
- クライアントはサーバーから受け取った時刻情報を起点に、次の同期まで表示上のカウントを補間する。
- サーバーから新しい時刻情報を受け取ったら、クライアント表示を正本へ補正する。
- ローカルPC版ではローカル用アダプターがサーバー側と同じ時計責務を担う。
- Matchへクライアント自己申告の経過時間をそのまま加算するAPIは置かない。

Matchは対局ルールと状態遷移を担当し、信頼できる現在時刻の取得、通信遅延の扱い、切断猶予などはサーバー側の時計サービスが担当する。Matchが残り時間や時間切れ結果を保持する場合も、その更新命令は信頼できるサーバー側からだけ与える。

## 終局と勝敗確定

- パス・パスで分かるのは、着手を止めて結果確認へ進むことだけである。
- パス・パスや手数上限だけから、Matchやサーバーが勝者を推測しない。
- 日本ルールなどでは死活と地の合意が必要であり、初期局面のパス・パスだけでは勝敗を計算できない。
- Matchは `Playing` から `AwaitingResult` へ進み、結果合意を待つ。
- 原則として、プレイヤー双方の結果申告が一致したら勝敗を確定する。
- 申告が一致しない場合は、対局再開または審判裁定へ進める。
- 審判裁定はサーバー運用上の権限であり、Matchが囲碁を完全解析して代行するものではない。
- 投了はプレイヤー自身による結果申告なので、相手の勝ちとして確定できる。

現行ローカルGUIには、パス・パス後に純碁の簡易採点を行う既存機能がある。第3段階では互換性のためローカル用ラッパーにだけ残し、Matchには入れない。将来のWebサーバーはこのローカル簡易採点を勝敗確定に利用しない。

### 結果申告と審判裁定

Matchの結果は表示文字列ではなく、黒勝ち、白勝ち、持碁、無勝負と、勝ちの場合の任意の差を持つ構造化データとして扱う。

- `AwaitingResult` では黒白がそれぞれ結果を申告できる。
- 片方だけの申告、または異なる申告では結果待ちを続ける。
- 同じ申告の再送は冪等に扱い、リビジョンを増やさない。
- 黒白の申告が一致したら結果を確定し、`Completed` へ進む。
- 不一致時はサーバー側判断で申告を破棄して `Playing` へ戻せる。
- 審判裁定は申告内容にかかわらず、構造化された確定結果を適用できる。
- 結果申告、合意、再開、裁定はすべて観戦イベントへ記録する。

プレイヤー本人であること、対局参加者であること、審判権限があることの確認はWebサーバーが担当する。Matchは認証済みの命令を決定論的に適用するだけである。

投了は投了者自身の申告なので即時確定し、構造化結果も同時に生成する。

## 対局履歴と保存用棋譜

Matchが持つ履歴と、GUIが保存する棋譜は責務を分ける。

### Matchが持つもの

- 盤サイズ、手数上限、開始手番
- 初期配置の黒石と白石
- Matchが受理したPlay、Pass、Resignの操作履歴
- 操作者、交点、取った石数、リビジョン
- 現在局面を再現するためのスナップショット

### GUIやサーバー外層が持つもの

- 対局名、プレイヤー表示名、段級位、場所、日付
- コメント、評価値、読み筋、GTP解析JSON
- SGF固有のプロパティとファイル入出力
- 自動保存先、レビュー表示、チャート表示

Matchの操作履歴は通信方式や保存形式に依存しない事実だけを保持する。GUIはMatchの結果を受けて、従来の `GoGameRecord` へコメントや解析情報を加えて保存する。将来のWebサーバーも同じMatch履歴を、データベースや配信用イベントへ変換できる。

盤面編集局面から開始するときは、GUIが現在盤面を `MatchConfiguration` の初期配置へ変換する。初期配置と対局開始後の操作履歴を混ぜない。

## SGFは棋譜を含む文書

SGFは着手列だけではなく、ゲーム木、変化図、コメント、評価値、勝率、読み筋、対局情報、独自拡張を保持できる。Matchの操作履歴より大きな概念として扱う。

将来SGFモデルを本格的に拡張するときの名前は `SgfDocument` を第一候補とする。`Record` より `Document` の方が、棋譜を含みながら観戦・検討・解析情報も包む性質を表せる。

```text
MatchActionRecord
  └─ 対局中に受理された操作の事実

SgfDocument
  ├─ SgfGameTree
  │   └─ SgfNode
  │       └─ SgfProperty
  ├─ 着手と変化図
  ├─ コメントと検討情報
  └─ 勝率、読み筋、独自解析情報
```

現行 `GoGameRecord` は単一の主変化を中心としたGUI用保存モデルであり、すぐには改名しない。ゲーム木や汎用SGFプロパティを表現できるモデルへ拡張するときに、`SgfDocument`、`SgfGameTree`、`SgfNode` への移行を行う。

## GTPプレイヤーとの境界

- GTPプロセスの起動、標準入出力、タイムアウト、ログはGUI側アダプターが担当する。
- MatchはGTPコマンドや外部プロセスを知らない。
- GTPが返した着手、パス、投了だけをMatchの操作APIへ入力する。
- Matchの初期配置はGUI側アダプターが `boardsize`、`komi`、`clear_board`、`play` コマンド列へ変換する。
- コンピューターが生成した着手をMatchが拒否した場合、GUIはGTPエンジンエラーとして扱う。

GTP標準の基本コマンドだけでは、任意の編集局面を必ず一括設定できるとは限らない。現在は初期配置石を `play` で順に送る。通常の合法な編集局面には対応できるが、途中で自殺形になる配置などを外部エンジンが拒否する可能性がある。将来は `loadsgf` 対応の能力確認や、エンジン固有の局面設定機能をオプションのアダプターとして追加できる。

## サーバー確定時計の同期

Matchは現在時刻を自分で取得せず、信頼済みのサーバー側時計サービスが決定した完全な時計状態だけを受け取る。

時計同期には次を含める。

- サーバーが発行する単調増加シーケンス
- サーバー上の同期時刻
- 黒と白それぞれの残り時間
- 現在手番の期限。時間制によって不要なら省略可能

Matchは古い時計シーケンスを拒否し、残り時間の巻き戻しや順序逆転を防ぐ。時計同期は着手数を増やさないが、観戦可能なMatchリビジョンを進める。

Matchの公開APIだけでは呼び出し元の認証は行えない。Webサーバーは認証済みの内部時計サービスだけに時計更新APIを呼ばせ、クライアントから届いた値を直接渡さない。ローカルPC版はローカル用時計サービスを信頼元とする。

クライアントは同期時刻と手番期限を使って表示を補間する。クライアント上のカウント値は表示専用であり、次のサーバー同期を上書きしない。

## 観戦イベント

Matchは通信プロトコルに依存しない、連番付きの状態変更イベントを保持する。

- 受理されたPlay、Pass、Resign
- サーバー確定時計の同期
- そのリビジョンにおける対局段階、終局理由、勝者

観戦側は最初にスナップショットを取得し、その後は既知のリビジョンより新しいイベントだけを取得できる。HTTP、WebSocket、再送、永続化、観戦者管理はサーバー側ラッパーが担当する。

現在のMatchイベント列はメモリ上にある。将来のWebサーバーでは、イベントをデータベースまたはイベントログへ保存し、Matchプロセス再起動後や長時間切断後にもスナップショットと差分を復元できるようにする。

## 任意局面を渡すGTP拡張の検討

自由な置き碁、詰碁、研究局面、途中局面からの対局には、黒白の任意配置を一括して渡せる仕組みが有用である。独自コマンドをすぐ固定せず、関心のある開発者と用途を集めてから提案する。

検討時には少なくとも次を扱う。

- 盤サイズ、コミ、ルール、開始手番
- 黒白の任意初期配置
- コウや直前局面など、合法手判定に必要な履歴
- 配置途中の自殺形に影響されない原子的な局面設定
- `known_command` などによる能力確認
- SGF断片を渡す方式と、交点一覧を渡す方式の比較
- エンジンが未対応の場合の明確なフォールバック

この拡張はGTPアダプターの責務とし、MatchのAPIやデータ型をGTP固有仕様へ合わせない。

- 中核: 対局セッション、参加者、盤面、手番、時計、着手、投了、終局、観戦用イベント
- ローカル用入口: GUIから中核APIを呼ぶアダプター
- Web用入口: Ubuntu上のASP.NET Coreホスト、認証、HTTP/WebSocket、データ保存
- 表示側: Windows GUIや将来のWebクライアント

これにより、ローカル対局とWeb対局で中核ロジックを共有しつつ、通信障害や認証などWeb固有の事情を中核から分離する。

## 着手時の注意

- 既存のローカル対局コードを一度に移さず、最初に公開APIと依存関係を決める。
- APIは画面操作ではなく、利用者が行いたい操作を表す。
- 対局状態の更新結果やイベントは、ローカルでもWebでも同じ意味になるようにする。
- Web化すると同時実行、切断と再接続、権限、永続化が必要になるため、中核APIへUIオブジェクトやソケットを渡さない。
- プロジェクト作成と移設は別作業として、既存ローカル対局の責務を調査してから段階的に行う。

## プロジェクトの依存方向

```text
KifuwarabeGo2026.Gui       ─┐
                             ├─> KifuwarabeGo2026.Match ─> KifuwarabeGo2026.Shared
将来のWebサーバーホスト   ─┘

KifuwarabeGo2026.Engine ────────────────────────────────> KifuwarabeGo2026.Shared
```

`Match` からGUI、Webサーバーホスト、Engineへは依存しない。
