# ゲーム構成要素と境界の用語整理

## 目的

`Provider Engine` という名称だけでは責務が伝わりにくいため、ゲームを構成するオブジェクトと、その境界に使う用語を整理します。

この文書は将来の設計に向けた用語案です。現行コードや既存プロトコルに残る `Provider` を、ただちに一括改名することを定めるものではありません。

## 全体像

```text
プレイヤー ── P ──┐
プレイヤー ── P ──┤
                  ゲームマスター ── G ── GUI
プレイヤー ── P ──┤
                  │
                  R
                  │
           ゲームルールエンジン
                  │
            設定／ルールセット
```

ゲームマスターはゲームの進行を統括し、プレイヤー、GUI、ゲームルールエンジンを接続します。ゲームルールエンジンは、局面と着手に対するルール上の判断を担当します。

## オブジェクト

### ゲームマスター

ゲームマスターは、ゲームの開始、手番、入力、ルール判定の依頼、終了、記録を統括する進行管理オブジェクトです。演奏における指揮者に相当します。

「インターフェース」と呼ぶと、プログラム言語上の `interface` や通信境界と混同しやすいため、「進行役」または「ゲーム進行エンジン」と表現します。

囲碁の対局、指定局面戦、ポン抜きなどは、ゲームマスター自体ではなく、ゲームマスターが実行する「ゲームモード」または「進行形式」として区別します。

- ゲームマスター: 進行を実行する仕組み
- ゲームモード: どのように進行するかを定めるもの
- 棋譜: 進行によって生成される記録

### プレイヤー

プレイヤーはゲームマスターへ接続し、対局者としてゲームへ参加する人またはコンピューターです。

基本的な責務は、ゲームマスターから局面と手番を与えられ、その局面で選んだ一手を応答することです。

### GUI

GUIは、設定の編集、ゲームへの入力、観戦、研究、および各画面へのナビゲーションを提供します。「きふわらべの碁2026」はGUIを含みます。

GUIはルールを独自に確定せず、ゲームマスターから通知された状態と、ゲームルールエンジンによる判定結果を表示します。

### ゲームルールエンジン

ゲームルールエンジンは、ゲームルールを計算として提供するプログラムです。主な責務は次のとおりです。

- 局面の保持または再構築
- 着手の合法性判定
- 着手適用後の局面計算
- 盤上から取り除かれる駒や石の計算
- 終局条件と勝敗の判定

囲碁、五目並べ、リバーシ、チェスなどは「ゲーム種別」です。日本ルールや中国ルールなど、同じゲーム種別の中で異なる規則は「ルールセット」と呼びます。

### ゲーム設定

従来の「コンフィギュレーション」は、性質の異なる値を含む上位概念として「ゲーム設定」と呼びます。

```text
ゲーム設定
├─ ルール設定
│  ├─ ルールセット
│  ├─ 盤サイズ
│  ├─ コミ
│  └─ 禁止手など
├─ 進行設定
│  ├─ ゲームモード
│  ├─ 初期局面
│  └─ 終了条件
└─ 時計設定
   ├─ 基本時間
   └─ 秒読み
```

持ち時間の進行管理は原則としてゲームマスターが担当します。時間切れを勝敗へ反映する必要がある場合は、その結果をルール側の判定へ渡します。

## 境界

| 記号 | 推奨名称 | 接続対象 | 主な内容 |
|---|---|---|---|
| P | プレイヤープロトコル | ゲームマスターとプレイヤー | 着手要求、着手応答、着手通知、投了 |
| G | GUIプロトコル | ゲームマスターとGUI | 操作入力、状態通知、表示更新、画面遷移 |
| R | ルールAPI | ゲームマスターとゲームルールエンジン | 合法手判定、着手適用、局面更新、終局判定 |
| C | 設定スキーマ／設定API | ゲームルールエンジンとゲーム設定 | 設定の記述、読み込み、検証、適用 |

P、G、R、Cは、特定のデータ形式ではなく「どの役割同士を接続する境界か」を示す記号です。実装時には、それぞれの境界に適した通信方式やAPIを選びます。

### プロトコルP

プレイヤーとの境界です。GTPは代表的な実装候補です。

ゲームマスターはプレイヤーへ「この局面で一手を選ぶ」よう要求し、プレイヤーは選んだ着手を応答します。また、他プレイヤーの着手やゲーム終了など、進行に必要な情報をゲームマスターから通知します。

### プロトコルG

GUIとの境界です。JSONなどの構造化データを利用できます。

GUIからは利用者の操作を入力し、ゲームマスターからは局面、消えた石、手番、棋譜、結果などを通知します。GUIは通知を受けて画面表示を更新します。

### ルールAPI R

ゲームルールエンジンとの境界です。ゲームマスターが局面と着手を渡し、ゲームルールエンジンが合法性、適用結果、取り除かれた石や駒、終局状態などを応答します。

GTPまたは独自プロトコルを通信手段として利用することは可能ですが、GTPの一般的な主用途はプレイヤーエンジンの操作です。そのため、境界Rの役割はGTPそのものとは分けて定義します。

SGFは主に棋譜やゲーム木を保存・交換するデータ形式です。境界Rで局面や着手列を受け渡す形式として利用することはできますが、ルールAPI自体とは区別します。

### 設定スキーマ／設定API C

ゲームルールエンジンと設定の境界です。内部実装だけで完結する場合は、独立した通信プロトコルを設ける必要はありません。

設定項目の型、既定値、許容範囲、相互制約を表す場合は「設定スキーマ」、設定の取得、検証、適用を操作として提供する場合は「設定API」と呼び分けます。

## 推奨用語

| 日本語 | 英語 | 意味 |
|---|---|---|
| ゲームマスター／ゲーム進行エンジン | Game Master / Game Flow Engine | ゲーム全体の進行役 |
| プレイヤー | Player | 一手を選ぶ対局者 |
| ユーザーインターフェース | GUI / User Interface | 操作、表示、画面遷移 |
| ゲームルールエンジン | Game Rules Engine | ルールに基づく局面と結果の計算 |
| ゲーム種別 | Game Type | 囲碁、連珠、リバーシ、チェスなど |
| ルールセット | Ruleset | 日本ルール、中国ルール、純碁など |
| ゲームモード | Game Mode | 通常対局、指定局面戦、ポン抜き、四択クイズなど |
| ゲーム設定 | Game Configuration | ルール、進行、時計に関する設定の総称 |
| プレイヤープロトコル | Player Protocol | 境界Pの契約 |
| GUIプロトコル | GUI Protocol | 境界Gの契約 |
| ルールAPI | Rules API | 境界Rの契約 |
| 設定スキーマ／設定API | Configuration Schema / API | 境界Cの契約 |

## `Provider Engine` の扱い

`Provider Engine` は、初期局面の生成、着手監視、ルール判定、終局判定など複数の責務を含み得るため、名称だけでは役割を特定しにくい用語です。

新しい設計では、実際の責務に応じて次の語へ分解します。

- ゲーム全体の進行を担当するもの: ゲームマスター／ゲーム進行エンジン
- 着手や終局をルールに基づいて判定するもの: ゲームルールエンジン
- 両者の境界: ルールAPI
- ルールの振れ幅を表すもの: ルールセットおよびゲーム設定

既存の `Provider` コマンドや文書は互換性のために旧称として残し、変更するときはプロトコル互換性と移行手順を別途定めます。

## 将来の拡張

この分離により、ゲームマスターとGUIを再利用しながら、ゲームルールエンジン、ルールセット、ゲームモードを差し替えられます。通常の囲碁だけでなく、変則囲碁、囲碁の四択クイズ、連珠、リバーシ、チェスなどへの拡張を想定できます。
